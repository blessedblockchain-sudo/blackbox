## Lifecycle gotchas found by the spike
- An ephemeral permission survives `commit_and_undelegate` of its account on the TEE (data intact, 0 lamports) and keeps enforcing privacy after re-delegation, but `CreateEphemeralPermission` then fails with `InvalidAccountData`. Check existence with `data_is_empty()`, not lamports, and close permissions (`CloseEphemeralPermissionCpi`) and ephemeral accounts before undelegating (the real program does this in `end_round`).
- Deploying a bigger binary needs `solana program extend` first; a failed `anchor deploy` leaves a buffer holding ~3 SOL (`solana program close --buffers`).
- On Node 22 the SDK needs `uuid` pinned to ^11 (pnpm override) and Anchor 0.32's `provider.sendAndConfirm` mangles web3.js 1.99 errors into "Unknown action 'undefined'"; use `sendAndConfirmTransaction` from web3.js to see logs.

## Findings while building BLACKBOX on the local stack (2026-09-11, late)
- **One ER deposit per wallet (local).** A second `delegateSpl` from a wallet whose ephemeral ATA is already delegated fails both ways: the non-idempotent path's `transferToVault` rejects the delegated eATA (`Invalid account owner`), and the idempotent shuttle path fails inside `SetupAndDelegateShuttleEphemeralAtaWithMerge` with `Transfer: insufficient lamports 500000, need 1392000` (the local eSPL program funds the shuttle with 500,000 lamports). Not yet tested on devnet. BLACKBOX deposits once per wallet per round: the bankroll comes from a fresh house wallet, agents deposit a licensing budget with their entry, backers use fresh wallets. `BlackboxClient.depositToEr` tries the shuttle for top-ups and fails with a clear message.
- **Never read a wallet's ATA through the ER before its first deposit.** The ER clones it as a plain account and later ER writes to it fail with `InvalidWritableAccount`. Check `hasErDeposit` (the eATA exists on L1 and is owned by the delegation program) first.
- **The TEE filters simulations too.** A simulation signed by a backer that touches the author's private Strategy (`tick_license`) comes back empty (0 CU, no error). The crank itself runs server-side and is unaffected (the e2e shows license ticks advancing).
- **Compute.** `tick_entrant` and `tick_license` run once per round tick (`ran_tick` guard), so a simulation usually returns early (~7.9k CU). `scripts/measure-cu.ts` samples at random offsets within the tick and reports the maximum: 16.8k-25.2k CU for the full path on the opt-level-3 build, 8-13% of the crank's 200k per scheduled instruction.
- **Program size and devnet rent.** opt-level 3: 1,197,680 bytes, 6.08 SOL rent-exempt on devnet. opt-level "z" (now the release profile): 923,560 bytes, 4.69 SOL. An upgrade needs a second full-size buffer while the program data stays funded.
- **Layout changes need a fresh stack.** After a field is added to `Round`, the refreshed IDL cannot decode a round created by the previous build ("Invalid bool", offset errors). Restart the local stack after account layout changes.
- **Process hygiene.** `pkill -f <pattern>` inside a chained shell command also matches that shell (its command line contains the pattern) and kills the chain. `scripts/local-stack.sh down` now waits for the old processes and force-kills stragglers, and `up` refuses to start while 8899 still answers; before this, a surviving old validator passed the new one's health check.
