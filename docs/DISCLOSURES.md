# BLACKBOX disclosures

Plain statements about what BLACKBOX hides, what it does not, whom you trust, and how the money works. They describe the code on 2026-09-11. If a statement here and the code disagree, the code is what runs; please report the difference.

## Status and money

1. **Nothing here is mainnet.** The BLACKBOX program is deployed on devnet (`BXAbfrYjTM7WQ7K6Rrj1epcQwd6jT3TTXs3yqTp1dx27`) and a full round was verified there against MagicBlock's TEE validator, 42/42 checks. Every MagicBlock primitive it uses was verified first on devnet and devnet-tee with a separate spike program (32/32 checks). There is no mainnet deployment, and running one would need an audit and a frozen or multisig upgrade authority first (item 7).
2. **"USDC" is a test token.** On the local stack and on devnet, the round's USDC is a 6-decimal SPL mint created by the round admin, who can mint any amount (the devnet mint is `9D8FWf2m4VqiPxbLCRgrpc929UBKoV52mjqnaXTMVy4E`). It is not Circle's USDC and has no value. Entry fees, margin, PnL, license fees, the house bankroll and prizes are real token transfers of that test mint.
3. **Local prices are mirrored, not live-pushed.** On the local stack there is no MagicBlock oracle pusher. `scripts/run-round.ts` (and the e2e test) read the real SOL, BTC and ETH Pyth Lazer accounts on devnet-tee every 2 seconds and write those prices into program-owned mock feed accounts on the local rollup every 500 ms. The mock accounts use the exact Pyth Lazer byte layout, and only a build with the `local-oracle` feature accepts them. Local marks can therefore lag the devnet feed by a few seconds and move in steps. On devnet the program reads the Pyth Lazer accounts directly.
4. **Local privacy is emulated.** The local "TEE" is MagicBlock's query-filtering service in front of an ordinary ephemeral validator. It enforces the same auth tokens and permissions, but there is no enclave and no attestation (the SDK's `verifyAttestation()` returns `true` on local without checking). The raw local rollup RPC on port 7799 has no read filter at all; it exists only inside the development machine and is not part of a production deployment.

## Hardware and operator trust

5. **You trust Intel TDX and MagicBlock's TEE validator.** On devnet the rollup runs on MagicBlock's TEE validator (`MTEWGuqxUpYZGFJQcp8tLN7x5v9BSeoFHYWQQ3n3xzo`) inside an Intel TDX trust domain. Clients check the enclave's attestation with `verifyTeeRpcIntegrity` from MagicBlock's SDK (the devnet round verified the TDX quote; the PCCS fetch is occasionally flaky and is retried). Attestation shows that the RPC endpoint runs attested code inside TDX; it does not remove the trust in Intel's hardware and firmware or in the attested software.
6. **What the operator could see in principle.** The operator of the TEE host controls the machine around the enclave. Without breaking TDX, it can see network traffic metadata (who connects, when, and how much), transaction timing and ordering, and it can delay, reorder or censor transactions and crank execution. It cannot read enclave memory unless TDX, its firmware, or the attested validator software is compromised (for example by a side channel or a vulnerability). If that happens, every strategy, position and license in the round is readable. BLACKBOX has no second line of defense against a compromised enclave.
7. **You trust the program upgrade authority.** The BLACKBOX program is upgradeable. Its upgrade authority is a single developer key (`3fMoA42W8MzvA86ZUFiRj5ayoEuwmDkz1qtZGiY5ooWR` on the local stack and for the devnet spike), which could ship a version that adds a reader to a permission or copies bytecode into a public account. Freezing the upgrade authority or moving it to a multisig is required before real money.
8. **You trust the round admin for round parameters, not for your code.** The admin creates the round, chooses markets, fees, margins, tick interval and duration, starts the round, chooses lit or dark, closes the chat and sweeps the vault at the end. The admin is not a member of any Strategy, Position or License permission and cannot read them: the permission's authority is the gated PDA itself, which only the program can sign for.

## What is private

9. **Strategy bytecode** is readable only by its owner's TEE auth token, during the round and after it. It is never written to Solana L1 in plaintext: the account is created zeroed on L1, filled only by rollup transactions, and zeroed again before it is committed. The `set_strategy` transaction that carries the bytes is hidden from non-members by the permission's `TX_MESSAGE` flag. Settlement scrubs the account but deliberately leaves the permission open, because closing it would also drop that redaction and expose every past upload in rollup history; the e2e checks a stranger's view of the upload transaction after settlement (verified in the spike, by `bx-attack`, and by `tests/blackbox.e2e.ts`).
10. **Position** (legs, margin, realized PnL, VM memory, step counts, faults, liquidation flag) is readable only by its owner's token, and is zeroed before commit.
11. **Token balances** of custody and vault accounts on the TEE are shown only to the owning wallet's token (spike bet 3). Entrant margin sits in a custody account owned by the Entrant PDA and a licensee's margin in one owned by the License PDA; the program publishes aggregates instead (below).
12. **After the round**, the private bodies on L1 are all zeros — checked by the e2e test for every entrant account and for the License — and `undelegate_entrant` and `undelegate_license` refuse to commit a private account whose body is not.

## Blind licensing

13. **A License is private to exactly two wallets.** `activate_license` gives the License an ephemeral permission whose members are the buyer and the author. The buyer reads their own book (margin, legs, realized PnL, fees accrued, the locked fee) and never the code that trades it: the Strategy permission lists only the author, and the e2e test checks that the backer's own token reads that strategy as `null`. The author is the other member, so backing a strategy shows its author your margin, your legs and your PnL on it.
14. **A licensee can infer the strategy's trades from their own fills.** The crank runs the author's sealed bytecode against the licensee's own private book, so the licensee sees every position it takes with their capital, tick by tick, and can reconstruct the trades even though the logic stays sealed. The code is private; what it does with your money is not.
15. **The license fee is priced inside the TEE and locked at activation.** `Entrant.fee_price_bps` is recomputed on every tick from the author's private per-tick return series: a rolling Sharpe ratio times 100, clamped to 0-300, mapped linearly onto the round's `[license_fee_min_bps, license_fee_max_bps]`; fewer than 20 samples, or a Sharpe at or below zero, gives the minimum. That price is public and is the only published trace of an author's performance besides the lit scoreboard — it says "this book has been steady", not what it holds. A license pays the price that was current when it was activated, charged on traded notional and taken out of the license's realized PnL.

## What is public by design

16. **Per entrant, every tick, in lit rounds:** equity, amount deposited, number of trades, alive or liquidated (the Scoreboard).
17. **Per entrant, always:** the Entrant record, including `strategy_version`, `fee_price_bps` and `license_count`. The version counter reveals that, and when, an owner hot-swapped, but not what changed; the license count reveals how many backers an author has taken.
18. **Per market, always:** mark price, EMA(8/21/55), realized volatility, the last 64 marks, open interest long and short, funding index and rate.
19. **Per round, always:** status, tick, parameters, pot, vault balance, total equity (the sum of all entrants' equity, public even in dark rounds), the number of open licenses, the VRF seed and the mystery market.
20. **After settlement:** each entrant's final equity, rank, and the sha256 of their final bytecode. The hash lets anyone verify a strategy that is later disclosed; it does not reveal the strategy.
21. **Dark rounds** hide the Scoreboard (program-only) until `close_round` commits it to L1. Round totals, Markets and Entrants stay public.
22. **The round chat is public and unmoderated.** `post_chat` writes into a 32-message ring buffer that lives only on the rollup. Any wallet can post 1-79 printable characters while the round is open or live, and anyone can read them; each message carries the author's public key, the tick and a timestamp. There is no filter, no rate limit and no deletion — the ring simply overwrites the oldest message after 32 posts. Nothing you type there is private, and it is not a side channel for strategy details. The chat never reaches L1: `close_chat` closes the account and refunds its rent to the Round before the round commits.

## Metadata and inference

23. **Timing and existence of transactions.** Hiding a transaction's message does not hide that it happened. Observers can see that an entrant's accounts were touched, and when; a hot-swap also bumps the public `strategy_version`, and activating a license bumps the author's public `license_count`. On the local stack, a stranger's `getTransaction` for a `set_strategy` signature returns the transaction with its instructions redacted (0 instructions, 0 bytes of data), as observed by `bx-attack`.
24. **Crank activity is regular by construction.** Every entrant's tick and every license's tick run on the same schedule whether or not the strategy trades, so tick timing alone does not reveal trading. Its effects do (next items).
25. **Open interest is public and updated inside each tick.** In a market where few entrants trade, a change in `oi_long` or `oi_short` can reveal one book's trade size and direction, and an observer sampling Market accounts between individual tick transactions may attribute a change to a specific entrant or license. Aggregating open-interest updates per clock tick would close this; it is not implemented.
26. **A lit equity curve leaks exposure.** Each entrant's equity is published every tick next to public marks. Regressing equity changes on mark changes estimates that entrant's net exposure per market over time. The logic stays sealed; its positions can be approximately inferred. Dark rounds remove the per-entrant curve.
27. **`RAND` is reproducible after the seed lands.** The VRF seed is stored in the public Round, and `RAND = sha256(seed, owner, tick) mod 1e6` (for a license, the buyer's key stands in for the owner). Anyone can compute any book's random draws once the seed is set. Before the VRF callback lands the seed is all zeros, so early-tick draws are predictable.

## Economics

28. **The round vault is the counterparty.** There is no order book and no outside liquidity. Every fill — for an entrant's own book and for a licensee's — is at the oracle mark plus or minus a spread (a base spread, plus a skew component when the trade adds to the long/short imbalance). The vault receives spread and the losses of losing books; it pays the profits of winning ones at settlement. This is a competition ledger with real token movements, not a venue.
29. **Profits are capped by what the vault holds, and the house bankroll is what keeps that cap off.** At settlement a profitable book is paid `min(PnL, vault balance - pot)`: the entry-fee pot is reserved for prizes, so profits come out of what losers and the bankroll have left in the vault. `seed_vault` lets anyone add a bankroll before or during the round (the provided runner seeds 2,000 test USDC from a fresh house wallet and sweeps it back at the end), and the runner settles entrants losers-first in lit rounds, so in a normal round every profit is paid in full. The cap still binds if total profits exceed the bankroll plus the losers' losses, and a shortfall is not paid later. `settle_entrant` and `settle_license` are permissionless, so the actual order is decided by whoever sends first; the runner's order is a convention, not a guarantee. A two-pass settlement (collect all losses, then pay profits pro rata) would remove the cap; it is not implemented.
30. **Losses are capped at margin.** A liquidated book whose position goes below zero loses its whole margin and no more; the vault absorbs the rest.
31. **Scores and ranking.** The public equity is the program's mark-to-market value. Ranking is by final equity divided by amount deposited (return on deposit); the entry fee is not part of the deposit. Ties go to the earlier entrant. Licenses are not ranked and do not affect the scoreboard: they are a separate book with their own margin.
32. **Prizes and the sweep.** The prize pot is the sum of entry fees. A protocol fee (`protocol_fee_bps`, 500 bps = 5% in the provided scripts) is kept; the rest is split 50% / 30% / 20% to ranks 1-3 (with fewer than three entrants, unused shares go to first place). Prizes are paid on the rollup into the winners' token accounts; winners withdraw to L1 with Ephemeral SPL. Once prizes are paid and every entrant and license has settled, `sweep_vault` sends whatever is left in the vault — the bankroll, net trading losses and the protocol fee — to a token account the admin chooses; the runner sweeps it back to the house wallet that seeded it.
33. **Funding** accrues every 240 ticks at up to 10 bps of notional at full skew, charged to the crowded side and absorbed by the vault like any other PnL.

## Known limitations in this build

34. **The round clock is permissionless but bounded by wall time.** `tick_clock` still has no signer check: the Native Crank calls it every `tick_interval_ms`, and any wallet can also send it on the rollup. It now refuses to advance past the time actually elapsed — the tick may not exceed `(now - started_at + 1 s) / tick_interval_ms` — so a spammer can no longer run a round to `duration_ticks` early and force settlement. What remains is that anyone may help a lagging crank catch up, and that the bound has one-second resolution because it comes from the cluster clock.
35. **Extra tick attempts for an entrant or a license are no-ops.** `tick_entrant` and `tick_license` have no signer check either, but each book records the tick it last ran in `ran_tick` and returns early if it is asked to run twice in the same round tick. A third party can no longer execute a rival's strategy against its own VM memory, make it trade more often, or add extra zero-return samples to the private Sharpe accumulators that the blind price is computed from.
36. **A wallet can deposit into the rollup only once (local stack).** The first `delegateSpl` delegates the wallet's ephemeral ATA; a later top-up goes through the eSPL shuttle path, which the local stack's eSPL program rejects (it funds the shuttle with 500,000 lamports where the transfer needs 1,392,000). BLACKBOX therefore deposits once per wallet per round: the bankroll comes from a fresh house wallet, agents deposit their licensing budget together with their entry, and each backer uses a fresh wallet. `BlackboxClient.depositToEr` attempts the top-up and fails with that explanation. This has not been tested on devnet, where every wallet in the verified round also deposited exactly once.

## Not claimed

37. BLACKBOX does not claim that trading performance on the leaderboard is achievable on a real venue: fills are at an oracle mark with a modeled spread, with no slippage beyond the spread formula and no counterparty other than the vault. Nor does a blind price claim that an author will keep performing; it is a number computed from that round's own returns.
38. BLACKBOX does not use session keys or the Magic Router in this build. Wallet approvals are per transaction, and clients address the base layer and the TEE endpoint directly.
39. The web app, compiler, MCP server, agents, attacker CLI and indexer are built and tested (counts in the README), but nothing they do is part of the on-chain guarantee: their privacy properties are those of the program and the TEE RPC described above. The MCP server and the web app's local mode hold keypairs on the machine that runs them. The web app's blind-licensing flow has been run only against a local round; its devnet path, which signs from a browser wallet, is untested.
