# Solana Blitz v8 — full idea pool (24 candidates, generated 2026-09-10)
Generated by 8 ideation angles. Judge scorecards exist for 6 ideas (the run was stopped to save session limit).

## Blackbox Arena  (`agents#1`)
**Tags:** DeFi, AI/Agents, Privacy  
**Primitives:** PER, ER, Ephemeral SPL, Oracle, Native Crank, Session Keys, Magic Actions, VRF

**Pitch.** An agent-vs-agent perps arena where every bot's strategy is compiled to bytecode and executed by the program itself inside the Private ER, so nobody, not the other bots, not spectators, not even the rollup operator, can read what a strategy does while it trades 4x per second against live Pyth feeds. At round end the TEE reveals only the leaderboard and pays the vault out on L1 in one Magic Action. The kicker: humans can license a winning agent's strategy for their own capital without ever being able to read it.

**Why only MagicBlock.** The whole product is 'a program executes secrets that clients cannot query'. On L1 the strategy bytecode is public the moment it is uploaded and every tick costs SOL at 400ms slots, so it is copyable, front-runnable and too slow. Off-chain, hidden strategies are just trust-me bots and licensing is impossible without leaking the code. Only a TEE-backed rollup gives (a) program-readable but client-unreadable accounts via Permission groups, (b) a zero-fee Native Crank to tick hundreds of strategies at 250ms, (c) Pyth Lazer pushed into the rollup at 50-200ms so strategies read price directly, and (d) Ephemeral SPL so licensing fees stream inside the rollup and settle on L1 once. Also 64KB ER tx size lets an agent hot-swap an entire strategy in one transaction.

**Demo moment.** Split screen. Left: 12 black boxes labeled Claude, GPT, Gemini, and 9 custom bots, each showing only an equity curve and alive/liquidated, while the MagicBlock explorer scrolls thousands of crank ticks. Right: a terminal runs an unauthenticated PER query on a Strategy account and gets permission denied; the owning agent's authenticated query returns the bytecode and Claude live-edits it ('cut my leverage, I am bleeding on BTC') and hot-swaps it in a single 64KB ER tx mid-round. Then the presenter clicks 'License Claude for 10 USDC' from a plain wallet; their capital starts mirroring trades within one tick while the strategy stays unreadable, and fee micro-transfers to Claude's eATA appear in the explorer every trade. Round ends, one Magic Action pays the vault out on L1 and the leaderboard becomes public.

**Architecture.** L1 (devnet): Round config PDA, Ephemeral SPL Global Vault for USDC (entry fees + prize pot), Permission groups (one per Strategy account = [owner]; one per Position account = [owner]), Leaderboard PDA (written only at commit). Delegated to the PER: Strategy accounts (8KB, created empty on L1 then filled ONLY via ER tx so plaintext bytecode never touches L1; read: owner only), Position accounts (size, entry, margin, unrealized PnL; read: owner only), each agent's eATA (private), MarketState per market (mark, OI, funding; public), License accounts (buyer position -> seller strategy link + fee bps; existence public, strategy still private). Oracle: Pyth Lazer SOL/USD, BTC/USD plus a pump.fun feed pushed into ER accounts, read directly by the tick. Native Crank: tick(strategy) every 250ms per strategy (isolated schedule per strategy so one bad program cannot stall the arena), liquidate_scan every 100ms, end_round once. The VM: a ~20-opcode stack machine (push, price(feed), position, equity, cmp, jmp, open_long/short(size), close, ema(feed,n)) with a hard step limit so a tick stays well under 200k CU. Licensing: License account points buyer's Position at seller's Strategy; the tick executes seller bytecode against buyer margin; 5 bps of notional per opened trade moves buyer eATA -> seller eATA via Ephemeral SPL CPI inside the rollup. Session Keys: the agents' MCP server (tools: get_market, compile_strategy, deploy_strategy, hot_swap, read_my_pnl) signs deploy/hot-swap with a scoped session key, no wallet popups; the human licensing UI uses a session key for one-click license/unlicense. VRF (optional, cheap): shuffle strategy tick order each slot so no bot can game execution priority. Settlement: end_round zeroes every Strategy and Position (commit = public, so private state is scrubbed first), writes final equities to Leaderboard, commits + undelegates Leaderboard and eATAs, and a Magic Action distributes the vault to the top N and pays accrued license fees to authors' L1 ATAs atomically. Fork the official Lever template for the vault/perps/liquidation skeleton and spend the week on the VM, permissions, licensing and agents.

**Novelty vs prior.** Ghost Stops put fixed order types (trailing stops, brackets) onchain; this generalizes to arbitrary hidden programs and the privacy is enforced by the TEE, not by obscurity. Tenor and Veil hide orders and positions but still have humans clicking; here the traders are LLM agents that author, read PnL, and hot-swap code through an MCP server. Oobe is a wallet/DeFi MCP; Loyal is cooperative yield agents; this is adversarial agents with hidden logic and real stakes. Official idea #2 ('private trading competitions') hides positions; this hides the strategy itself, executes it inside the rollup, and adds blind licensing, which no template or past winner has. Lever is reused only as plumbing.

**Risks.**
- A bytecode VM written in a week will have bugs; a strategy that panics must not stall the crank, so per-strategy crank schedules and a try/return-early pattern are mandatory from day 1.
- Unverified assumption: that a crank-executed instruction (program-signed, not owner-signed) can read a private account inside the PER. Confirm with MagicBlock engineers in Telegram on day 1; if not, the whole design collapses to 'hidden positions only'.
- Native Crank throughput at 100 strategies x 4 ticks/s = 400 ix/s is unknown; fall back to 500ms or 1s ticks if the scheduler throttles.
- PER is devnet only, so the arena runs on devnet USDC; TEE is a hardware-trust assumption and the pitch must say so plainly.
- Blind licensing leaks partially: a licensee can read their own Position account and infer the strategy from its trades. Say this out loud; the pitch is 'logic stays private', not 'trades stay private'.
- Judges may see the LLM layer as a thin wrapper around a DSL compiler. Counter by having agents visibly iterate on private PnL mid-round and by making the MCP server a real repo artifact.
- Pyth Lazer at 50-200ms vs 250ms ticks means strategies see slightly stale prices; not a demo problem, but no HFT claims.
- Anything undelegated is public: forgetting to zero Strategy accounts before end_round would dump every strategy to L1. Test this explicitly.
- Reusing the Lever template invites 'it is just Lever with a VM'; the demo must lead with the permission-denied query and the licensing, not the perps.

**One-week scope.** Day 1-2: fork Lever (vault, positions, mark price from Oracle, liquidation crank); add PER delegation and Permission groups for Strategy/Position/eATA; verify program-side reads of private accounts. Day 3: stack VM with step limit + tick(strategy) crank ix + hot_swap ix (64KB upload). Day 4: TS DSL->bytecode compiler + MCP server + run 4 LLM agents (Claude, GPT, plus two scripted) in a live round; equity curves on the explorer. Day 5: Round lifecycle, scrub-before-commit, Magic Action payout, License account + per-trade fee transfer via Ephemeral SPL. Day 6: Arena UI (black boxes, equity curves, license button, explorer deep links), permission-denied vs authenticated query demo script. Day 7: 3-minute video, README, submission with ER explorer proof. Cut order if behind: VRF tick shuffle, then licensing UI (keep CLI), then pump.fun feed.

**Extreme extension.** Blind alpha licensing: a strategy is an asset that earns fees from other people's capital while remaining unreadable by them, by the operator, or by the chain, plus a 'dark leaderboard' where only the TEE knows who is winning until the commit reveals it, and agents that rewrite their own strategy code mid-round in a single 64KB transaction.

- *magicblock-insider* overall 7.5 (depth 9, wow 8, feasibility 5, novelty 8, product 7). That turns the privacy claim from an assertion into a verifiable moment and closes the exact holes a MagicBlock judge would probe.
- *solana-user* overall 7 (depth 8, wow 7, feasibility 4, novelty 7, product 6). The most PER-native concept I have seen pitched for Blitz (the program executes secrets no client, spectator or operator can read, which is the one thing a TEE rollup does that nothing else on Solana can), but every degen will read the headline as Alpha Arena on MagicBlock, and it only takes 1st if the team survives a brutal scope and actually ships the hot-swap and blind-licensing beats rather than a Lever fork with equity curves. **Weakness:** Scope stacked on unverified integration bets: a perps-engine fork, a bytecode VM, an LLM/MCP agent layer and a licensing system all depend on Native Crank, Oracle push, Ephemeral SPL CPI and TX_MESSAGE privacy (for the 64KB hot-swap) working inside the single TEE validator, none of which is confirmed; and the kicker beat, blind licensing, is scheduled last and is the flimsiest on inspection, since a licensee reverse-engineers a 20-opcode EMA strategy from their own trade log in an afternoon, and copy-trading platforms already hide the leader's code on a server, so the real differentiator (verifiable, un-front-runnable execution) is subtler than the pitch admits. **Improve:** Drop the Lever fork and the real perps engine entirely: make positions paper-perps marked directly to the Pyth Lazer account (fixed leverage, liquidate at equity <= 0) settled from the entry-fee pot, and define licensing as 'enter the arena under a seller's private strategy, author earns bps of your entry and PnL'. That deletes vault, OI, funding and counterparty machinery, kills the 'it is just Lever with a VM' critique, and buys the two days needed to make the mid-round hot-swap and licensing actually land, which are the only beats that separate this from Alpha Arena and official idea #2.

## Dead Drop  (`agents#2`)
**Tags:** AI/Agents, Payments, Privacy  
**Primitives:** PER, Ephemeral SPL, Private Payments, VRF, Native Crank, Session Keys, Magic Actions, Ephemeral Accounts, Oracle

**Pitch.** A fully private labor market for AI agents: clients post jobs with a hidden budget, worker agents bid with a hidden ask, the program inside the Private ER matches them without either side ever learning the other's limit, the deliverable is dropped into the TEE where only the client can read it, and payment settles on L1 to a stealth handle. Disputes are decided by a VRF-drawn blind jury of staked agents who can read the work but not who did it. Winning agents can sub-contract pieces of a job to other agents from the same escrow, so a 20-agent swarm can build a report and the payment graph is invisible to everyone.

**Why only MagicBlock.** A both-sides-private negotiation needs a mediator that can read two secrets and reveal only the outcome; on L1 every budget, bid and deliverable is public, and off-chain the mediator is a trusted company. The PER makes the program that mediator: budgets and asks sit in accounts readable by exactly one key, matching runs in one 10ms slot, and the Permission program lets read access be granted after the fact (the matched worker gets the spec, the jurors get the deliverable). Ephemeral SPL provides escrow that lives in the rollup and settles once on L1, the Native Crank enforces deadlines and voting windows for free, VRF supplies unbiased surplus splits and jury draws, and the Private Payments API turns the payout into a stealth-handle transfer so the client's L1 history shows one transfer, not five workers. None of this stacks on vanilla Solana.

**Demo moment.** A client agent posts 'write a 10-page market report' with a hidden 40 USDC budget; 20 worker agents bid with hidden asks; the match lands in one ER slot at a VRF-randomized price inside the overlap, and the presenter shows both agents' logs: each knows the deal price but neither can reconstruct the other's limit. The winner spawns four sub-jobs (research, charts, draft, review) funded from the parent escrow; other agents claim them and their deliverables land as dead drops. The presenter's unauthenticated PER query on the deliverable account returns permission denied; the client's authenticated query returns the report. One sub-worker delivers junk, the parent disputes, VRF draws 3 jurors on the explorer, they read the work but not the parties, vote 2-1, and the slashed stake moves to the jury. Approval fires a commit plus Magic Action that pays five workers to stealth handles while the client's L1 transaction shows a single transfer.

**Architecture.** L1 (devnet): Market config, Ephemeral SPL Global Vault (USDC escrow + juror/worker stakes), JurorPool registry, Permission groups managed by the program (Job=[poster], Bid=[worker], Deal=[poster, worker], Deliverable=[poster] extended with [jurors] on dispute, JurorVote=[juror]). Delegated to the PER: Job (spec hash, hidden budget, deadline, status), Bid (hidden ask, worker key, stake ref), Deal (price, parties, deadline, parent job ref), Dispute, JurorVote, poster and worker eATAs, JurorStake eATAs. Ephemeral Accounts sponsored by the Job account hold the full spec text and the deliverable chunks (written via 64KB ER txs, rent ~109x cheaper than L1); payloads are additionally encrypted client-side to the recipient's x25519 key so privacy does not depend solely on the permission layer. Matching: on each new bid the program checks ask <= budget, and if the overlap is non-empty requests VRF; the callback sets price = ask + r * (budget - ask) so the deal price reveals only a bound, not the counterparty's number (a plain midpoint would leak it exactly). Escrow: poster deposits USDC to the Global Vault, eATA delegated, program locks the deal amount on match. Sub-jobs: a Deal may open child Jobs funded from its locked amount with an allocated counter that cannot exceed the parent lock. Delivery: worker writes chunks, then calls deliver(hash). Approval: approve() commits Deal + eATAs and attaches a Magic Action that pays the worker via the Ephemeral SPL private transfer queue to worker@magicblock.id (stealth pool, payment splitting for multi-worker jobs), plus undelegate of the poster's remaining eATA for refund. Native Crank: deadline sweeper every 1s (auto-release after N ticks with no dispute, auto-refund if no delivery), and dispute window closer. Clock: the crank reads Pyth Lazer publish_time from the oracle account as a trusted timestamp instead of slot time (flagged for engineer confirmation). Disputes: dispute() stakes a bond, requests VRF, callback selects 3 jurors from JurorPool, adds them to the Deliverable and JobSpec permission groups (identities live in separate accounts they are not granted), jurors vote, majority decides, minority juror and losing party slashed to the majority. Session Keys: the MCP server (post_job, bid, read_spec, deliver, approve, dispute, vote) uses scoped session keys so agents run unattended. Scrub-before-commit: budgets, asks and payload pointers are zeroed before any commit so nothing private reaches L1.

**Novelty vs prior.** This is official idea #4 taken three levels further: hidden-reservation bilateral matching with a VRF surplus split (the sealed-auction template is one-sided and reveals the clearing price), a blind VRF-selected jury that gets read permission on the work but not the parties (a genuinely new use of Permission groups), and recursive sub-contracting from a shared escrow producing an invisible payment graph. Oobe's MCP wraps a wallet and swaps; this MCP is a labor protocol with mechanisms. Loofta Pay and the private-payments demo move money to a handle; here the stealth payout is the last step of an escrowed, disputable, multi-party workflow. Tenor is private RFQ for FX between institutions; this is agents hiring agents with deliverables transported through the TEE.

**Risks.**
- Whether Ephemeral Accounts can be placed in a Permission group is unverified (they do not exist on L1). Mitigation baked in: client-side encryption to the recipient key, with PER permissions as defense-in-depth; if that fails, pre-create fixed-size L1 accounts and delegate them.
- VRF surplus split only weakens the leak; a party can still learn a bound on the other's limit, and repeated interaction narrows it. Be explicit about the threat model.
- Blind jury is only as blind as the deliverable: work that contains identifying details de-anonymizes the worker. Also, in a week the jury is three LLM juror agents run by the team, not a real staked pool; say so.
- Reliable timeouts need a clock: slot time is unreliable per MagicBlock, and reading Pyth publish_time as a timestamp is a clever hack that must be confirmed with engineers or replaced with tick-counting in the crank.
- Deliverables are limited to text/code-sized payloads (tens of KB); no images or large files without off-chain storage, which reintroduces a trust hole.
- PER escrow is devnet while the Private Payments API is mainnet; the end-to-end demo is devnet Ephemeral SPL private transfers, with mainnet payouts described as the production path only.
- Recursive escrow accounting is an easy place to ship a double-spend; keep the allocated counter simple and test over-allocation explicitly.
- Scope is large (matching, escrow, delivery, disputes, sub-jobs, MCP, agents, UI); sub-jobs and jury are the first cuts and the demo survives without them, but loses its extreme edge.
- TEE trust assumption and the fact that the operator could in principle observe access patterns; do not claim more than the hardware gives.

**One-week scope.** Day 1-2: escrow program with Ephemeral SPL deposit/delegate, Job/Bid/Deal accounts in the PER with Permission groups, hidden-reservation match with VRF surplus split; prove permission-denied vs authenticated reads. Day 3: spec and deliverable dead drops (chunked 64KB writes, client-side encryption), deliver/approve, commit + Magic Action payout to a stealth handle, crank deadline sweeper. Day 4: MCP server and four agents (one client, three workers) running end-to-end unattended with session keys. Day 5: dispute flow with VRF jury and slashing; sub-jobs funded from parent escrow. Day 6: dashboard (job feed with redacted fields, explorer deep links, jury draw visualization), demo script. Day 7: video, README with threat model, submission. Cut order: sub-jobs, then jury (keep dispute = refund), then dashboard polish.

**Extreme extension.** Recursive private sub-contracting: a job becomes a private task DAG where a swarm of agents hires each other from one escrow, with VRF-drawn blind jurors adjudicating any node, and the entire payment graph collapsing into one stealth transfer on L1 so no observer can tell that 20 agents were ever involved.

**Judge scorecards.**
- *hackathon-veteran* overall 6 (depth 8, wow 6, feasibility 4, novelty 7, product 6). A genuinely PER-native build of official idea #4 with two clever mechanisms (post-hoc juror read permissions, VRF surplus split that hides the counterparty's limit), but the plan is 2-3x a survivable week and the parts that make it extreme are exactly the first cuts, so the probable shipped version is a well-executed private agent jobs board with a logs-and-redacted-dashboard demo that several other teams will also submit. **Weakness:** Scope and demo legibility together: nine primitives, four separate "wow" beats (permission-denied read, hidden match, jury draw, one-transfer payout), and unflagged compound infra risk (Ephemeral SPL vaults, VRF callbacks, and Native Crank all have to work on the TEE validator, not just a regular ER, and Ephemeral Accounts in permission groups is admitted-unverified). The differentiators (blind jury, recursive sub-contracting) are days 5 of 7 and first in the cut order, so the demo most likely becomes "private RFQ for agents" with no single visceral moment. **Improve:** Cut sub-jobs and the staked jury from the plan on day 0 (dispute = refund), spend the freed two days on a day-0 Telegram verification that Ephemeral SPL + VRF + crank run on devnet-tee, and rebuild the entire demo around one split-screen moment: the MagicBlock explorer on the left showing 20 hidden bids, the match, and five private payouts landing in ER slots, while Solana explorer on the right shows the client's single boring transfer, run live and unattended by real MCP agents with session keys.
- *magicblock-insider* overall 7 (depth 8, wow 7, feasibility 5, novelty 7, product 6). The most genuinely PER-native agent concept in the field (a confidential mediator for two-secret matching, post-hoc juror permission grants, and payload transport through the TEE), but the week-one scope plus several unverified TEE-side primitive interactions make it as likely to arrive as a polished official idea #4 as the extreme version that would take 1st. **Weakness:** Scope versus one week, compounded by architectural hand-waving on the exact demo punchline: the "Magic Action pays to worker@magicblock.id" path is not real (stealth handles are resolved by the hosted Private Payments API, not resolvable in-program), committing Deal leaves price on L1, the global sweeper crank cannot iterate jobs with a fixed account list, and Ephemeral SPL private transfers, VRF callbacks, ScheduleTask, and Ephemeral Account permissions are all unverified inside the TEE validator, while the cut order removes exactly the two features (blind jury, sub-jobs) that separate this from every other idea #4 submission. **Improve:** Rebuild the payout path so the punchline is provably true and verify it on day 1: route all payouts as in-PER Ephemeral SPL transfers from a program-owned escrow eATA to stealth keys workers register at bid time (the Global Vault is the L1 mixer; drop the Magic-Action-to-handle claim, and scrub price before committing Deal), then promote the blind-jury permission-group extension from a day-5 cut candidate to a day-2 core deliverable built alongside matching, since it is the one Permission-program use no template has and the thing a MagicBlock engineer would actually tweet.
- *solana-user* overall 7 (depth 8, wow 6, feasibility 4, novelty 7, product 5). A genuinely PER-native concept with two real mechanism inventions (VRF surplus split so the deal price leaks only a bound, and a VRF-drawn jury granted read permission on the work but not the parties) that could take 1st if the full arc ships, but it is official idea #4 in what will be a crowded jobs-board field, its customer is synthetic (no one today has agents paying 40 USDC to other agents for reports), and the scope will most likely be cut down to the parts every other jobs-board team also has. **Weakness:** The demand is imaginary and the demo is terminal logs: agent-to-agent commerce in 2026 is x402 calls for cents where hidden reservation prices do not matter, the staked juror pool is a cold-start problem, there is no viral loop or human face, and the three things that make it extreme (blind jury, sub-jobs, stealth multi-payout) are exactly the ones on the cut list and all depend on VRF, Native Crank, Ephemeral Accounts and Ephemeral SPL working together inside the TEE validator, which is far less proven than each primitive alone on a public ER. **Improve:** Put a human on the client side with a real task judges recognize (audit this Anchor program, write my token docs, fix this bug bounty) and let workers be a mix of humans and agents, so the pitch becomes 'Upwork where the client never sees your minimum rate and you never see their max budget' (instantly legible, real demand, a real take-rate business); then cut sub-jobs entirely and spend the saved days making the blind-jury dispute and the single-L1-transfer stealth payout the two polished showpieces with explorer proof, since those are the parts no other jobs-board team will have.

## Nightshift  (`agents#3`)
**Tags:** AI/Agents, Infrastructure, Privacy  
**Primitives:** PER, Ephemeral SPL, Native Crank, VRF, Session Keys, Magic Actions, Ephemeral Accounts, Private Payments

**Pitch.** A dark exchange for LLM inference where prompts, quotes and payments never leave the TEE: requester agents post private max prices, provider agents post private quotes tied to a model hash, the program matches them in one slot, the prompt travels to the provider through a private rollup account, tokens stream back as ephemeral-account writes every 200ms, and a crank meters USDC per token as they arrive. Flip on verified mode and the same prompt is dispatched to a VRF-chosen quorum of providers; outputs that disagree get slashed. It is official idea #5 rebuilt as a streaming market with agents on both sides instead of a job board.

**Why only MagicBlock.** Streaming pay-per-token is impossible on L1 (a 5-cent inference cannot afford 300 metering transactions at 400ms each) and a private orderbook is impossible without a TEE. The PER gives a program that can see both sides' prices and reveal only the match, accounts that hold the prompt and the response readable by exactly one key each, and Ephemeral SPL balances that the Native Crank can move per chunk at zero fee before a single L1 settlement. The 64KB ER transaction size is what makes prompts-as-payload practical at all, and Permission groups are what let a provider read the prompt and a requester read the response with nobody else, including the operator's RPC, able to. Without ER/PER this is either a public chain leaking every prompt or a Web2 API with an escrow promise.

**Demo moment.** An agent starts a research task and every one of its reasoning calls is routed through Nightshift: the screen shows the prompt ciphertext landing in a PER account, a match in a single slot, tokens streaming back as ephemeral-account writes every 200ms, and the requester's USDC balance ticking down per token on the MagicBlock explorer while the operator's unauthenticated query returns permission denied. Then the presenter toggles verified mode: the next prompt fans out to three providers, two output hashes agree, the third (a rigged provider returning junk) disagrees, and the audience watches the crank slash its stake and a Magic Action credit the two honest providers on L1, all before the agent finishes its next paragraph.

**Architecture.** L1 (devnet): Exchange config, Ephemeral SPL Global Vault (requester deposits, provider earnings, provider stakes), Provider registry (pubkey, model hash, engine hash, stake), Permission groups managed by the program (Quote=[provider], Request=[requester], Session=[requester, provider], PromptBlob=[provider], ResponseStream=[requester], ProviderStake=[provider]). Delegated to the PER: Quote accounts (price per 1k tokens, capacity, model hash, private so providers cannot undercut each other by one lamport like a dark pool), Request accounts (max price, prompt hash, mode, private), Session accounts (matched pair, tokens delivered, USDC metered, private to the pair), requester and provider eATAs. Ephemeral Accounts sponsored by the Session hold the PromptBlob (written in one 64KB ER tx, also encrypted client-side to the provider's x25519 key) and the ResponseStream (append-only chunks the provider daemon writes every 200ms). Matching: on new Request, the program scans Quotes for model hash match and price <= max, picks the best price (VRF-random among ties so no provider gains a structural edge), opens a Session, adds the provider to the PromptBlob permission group. Metering: Native Crank meter(session) every 200ms counts new chunk tokens and moves price x tokens from requester eATA to provider eATA via Ephemeral SPL CPI; a no-first-chunk timeout after N ticks cancels the session and applies a small stake penalty. Verified mode: Request sets quorum=3; program requests VRF, callback selects 3 providers with the same model+engine hash, opens 3 Sessions, each provider writes chunks plus a final output hash; the program pays the majority and slashes the minority by committing its ProviderStake with a Magic Action transferring the slashed amount to the requester's L1 ATA. Session Keys: the requester's agent signs request/ack instructions with a scoped session key; providers run a TypeScript daemon (Ollama locally or an API-backed model for the demo) that authenticates to the PER, polls for Sessions it is permitted to read, and streams chunks. Settlement: Sessions close in-rollup (no L1 tx per session); providers withdraw by undelegating their eATA -> Global Vault withdraw, optionally to a stealth handle via the Private Payments API; requesters top up via deposit. Scrub-before-commit: Quotes, Requests and blob pointers are zeroed before any commit. MCP: an infer(prompt, model, max_price, mode) tool so any Claude/GPT agent becomes a customer, and a quote(price, capacity) tool so provider agents can re-price based on GPU load.

**Novelty vs prior.** Tenor is private RFQ for FX between humans; Nightshift is a continuous private market where the order payload is the prompt and settlement streams per token, with agents on both sides. Oobe exposes wallet operations over MCP; Nightshift's MCP is a marketplace where the agent's own reasoning is the product being bought. Official idea #5 is a job board with 'proofs verified'; this is honest about what proof is achievable in a week (VRF-sampled quorum execution with slashing rather than cryptographic proof of inference) and adds the two things no template has: prompts transported through private rollup accounts and crank-metered micropayments per chunk. The private-payments demo moves one transfer; here private payments are the exhaust of a live market.

**Risks.**
- Quorum verification assumes deterministic outputs; temperature-0 decoding still diverges across GPUs and engines, so exact-hash agreement only works for a pinned small model on a pinned engine. The demo must use that, and the pitch must not claim general verifiable inference.

**Pitch.** A battle royale of nerve around a live memecoin chart: up to 500 players stake USDC on one token, everyone starts long at the same price, and anyone can secretly bail at any moment, paying a penalty into the survivors' pool. **Architecture.** L1: ModelRegistry (model id, pinned engine version, weights hash), Offer per provider (PUBLIC: model, price per token, stake, reputation, endpoint hint), ProviderStake vault (USDC, program-owned, kept on L1 so slashing is a plain L1 transfer), USDC Global Vault via Ephemeral SPL, NetworkStats, and one ClientAccount per client (created and delegated once). Delegated to the PER: ClientAccount (PRIVATE; read permission = {client}), Session (PRIVATE; read permission = {client, provider}; fields: prompt bytes up to ~60KB, max tokens, price, chunk cursor, paid_so_far, state; sessions are ephemeral accounts sponsored by ClientAccount, or a recycled pool of eight L1-created Session PDAs per client if ephemeral accounts cannot carry a permission group), Response (ephemeral account sponsored by Session, resized as chunks append, closed on client ack so the transcript is destroyed), client and provider USDC eATAs, Offer accounts (public, delegated for live reputation updates), AuditCase (PRIVATE; read permission = {auditor, provider}). Flow: client deposits USDC to its eATA; `open_session(offer, prompt)` in one 64KB ER tx; the provider node (headless keypair plus session key) polls assigned sessions via the authenticated PER RPC, runs the model, and calls `append_chunk(tokens)` every 8 tokens; the program appends to Response and CPIs an Ephemeral SPL transfer of price x 8 from client eATA to provider eATA; the client can `cancel` at any time and payment stops at the last chunk. Crank: every 500ms sweep open sessions, 5s without a chunk marks the provider timed out, unlocks client funds and decrements reputation; every 10s process audit deadlines. Audit: on `close_session` the program requests VRF; with probability q (from the Offer's stake tier) the session is flagged and VRF picks an auditor from the same model's Offer set; an L1 crank job CPIs the Permission program to add the auditor to the session group; the auditor re-executes deterministically (greedy decoding, pinned engine, fixed seed) and submits a hash of the first 64 tokens; `finalize_audit` compares it to the provider's committed hash and on mismatch commits AuditCase plus reputation, with the attached Magic Action moving USDC from ProviderStake to the client (refund) and auditor (bounty) on L1 atomically. Providers withdraw by undelegating their eATA, optionally routing through the Private Payments API to a stealth handle so earnings are unlinkable on L1. Only eATA balances, reputation and audit verdicts ever commit; prompts and responses never do. Agents use a thin MCP tool (open_session, stream, cancel) backed by a session key.

**Novelty vs prior.** Oobe won with an agent MCP server and later private swaps and transfers; nobody has done inference with content-coupled streaming payments. **Risks.**
- Verifiable inference is unsolved. Hash-equality re-execution is fragile: floating-point nondeterminism across GPUs and engines produces false mismatches. Pinned engine version, first-64-token hash, greedy decoding and a dispute window reduce but do not eliminate false slashes. Say so in the pitch or a judge who knows ML will say it for you.
- Privacy is from the world and from L1, not from the provider: the provider sees the prompt, and VRF-selected auditors see sampled sessions. The honest claim is 'nobody but your provider and the TEE'. TEE trust is a hardware assumption and the PER operator can read state.
- Ephemeral SPL CPI from a custom program must be confirmed on day 1 (the spl-tokens example suggests it works); the fallback is internal ledger accounting in Session with one eSPL transfer at close, which guts the per-token story.
- Whether ephemeral accounts can carry a permission group is unknown; the L1 Session-pool fallback costs rent and delegation deposits per client and adds latency.
- Adding an auditor to a permission group is an L1 transaction, so audits take seconds and the auditor necessarily receives the prompt: an information leak by design, bounded by q.
- ER load: ~10 chunk txs per second per session; 100 concurrent sessions is 1,000 tx/s on one PER. Chunk size may have to grow to 32 tokens under load, which makes the balance ticker less dramatic.

- Inbox PDA [game, player]: ~8KB ring buffer of messages the program fans out. PRIVATE: G_i. Carries the traitor chat (fan-out to traitor seats only) and system whispers (role reveal, bribe notifications). Faithful inboxes get padded decoy writes each round so write patterns do not leak who is a traitor. Key design point: the 'traitor group' is never an L1 permission group, because L1 group membership is public; the TEE fans out to per-player private inboxes instead.
- PublicChat: Ephemeral Account ring buffer sponsored by Game. Public.
- BribeLedger PDA [game]: (from, to, amount, memo, ts). PRIVATE with an empty permission group (program-only) until reveal.
- Reveal PDA [game]: roles, votes per round, traitor chat, bribes. Public; written at the end.
- Ephemeral SPL: USDC Global Vault; per-player eATAs delegated; Pot eATA under program authority. Bribes are program-CPI'd private eATA-to-eATA transfers, logged in BribeLedger.
- L1-only Hall PDA [wallet]: games, wins as traitor/faithful, bribes taken; written by Magic Action.

FLOWS:
- /backstab 10 in Telegram -> bot creates Game and delegates; players tap JOIN in the Mini App -> embedded wallet + session key (Telegram CloudStorage); one-time approval deposits USDC to an eATA and grants the program authority for stake + bribe cap; bot creates Seat/Inbox + permission group G_i (sponsored) and delegates.
- Start: program requests delegated VRF from inside the ER; the callback deals roles into Seats and writes 'you are TRAITOR/FAITHFUL' into each Inbox; traitors also receive the names of their fellow traitors.
- Night (crank-timed, 60s): traitors whisper() -> program fans out to traitor Inboxes; night_target majority = kill; decoy writes go to faithful inboxes.
- Day (120s): say() -> PublicChat; bribe(to, amount, memo) -> private transfer + BribeLedger entry + whisper to the recipient's Inbox; vote(target) sealed in Seat.
- Resolve (crank): tally inside the TEE, banish, check win condition (all traitors out -> faithful win; traitors >= faithful -> traitors win), next round or END.
- End: program writes Reveal, pays the Pot to the winners' eATAs (bribes stay where they were sent, so taking a bribe is real money), commits and undelegates; the Magic Action updates Hall PDAs and emits the reveal event the bot renders into the card; players withdraw from the Global Vault or leave the balance for the next game.
- Session keys sign every in-game action. No oracle, deliberately.

**Novelty vs prior.** No prior Blitz winner is a party game; BlitzMine and the promoted Supersize/Slimecoin titles are real-time skill games, not hidden-information social games. Templates cover RPS (two-player hidden move); this is eight-player hidden roles plus hidden sub-chat plus hidden payments plus a full audit reveal, three layers further, and the first thing to use private payments as a game mechanic rather than a payment feature. It is distinct from all five official ideas (none are games without a price) and from Tenor/Veil/Ghost Stops (pro-trader products). The per-player inbox fan-out is a genuinely new PER pattern the engineers will notice.

**Risks.**
- A traitor group cannot be an L1 permission group because membership is public; the inbox fan-out fixes it but multiplies writes (one message -> k inboxes) and needs decoy writes so the pattern does not leak. Confirm on day 1 that per-account read permissions behave as documented and that the PER does not expose tx payloads or logs (a visible whisper() tx would leak). If Ephemeral Accounts cannot be permissioned, inboxes must be L1 PDAs, which is what the design assumes.
- Delegated VRF inside the PER is unverified. Fallback: request VRF into an account with program-only read permission before delegation; worst case TEE-generated randomness from the program, disclosed as weaker.

Fallback: bribes are ordinary eATA transfers whose parties and amounts are hidden only because the eATAs are permissioned, still invisible to other players.
- Scope is brutal: game loop, two chats, bribes, reveal, bot, Mini App. Ship a fixed 8-player, 3-round, 2-traitor format with no twists. Cut bribes last; they are the demo.
- Real-money social deduction is gambling-adjacent; frame as a stake-based party game (on-brand with Slimecoin/Supersize) and keep demo stakes small.
- Out-of-band collusion in side DMs is unstoppable; it is part of the game, and the bribe reveal partially disciplines it, but a judge may poke at it.
- Not trading: the judge who wants DeFi ranks it below a trading app. Counter: it is the deepest PER showcase they will see and the most 'send this to the group chat' product in the field.

- TEE hardware-trust assumption; PER is devnet-only so the demo is play money with real mechanics.

**One-week scope.** D1: Anchor game state machine on the public ER (join/start/whisper/say/vote/bribe/resolve/settle) with crank timers and VRF role dealing. D2: PER migration: Seats/Inboxes/BribeLedger permissioned, auth-token client, fan-out plus decoy writes. D3: Ephemeral SPL stake, bribe and payout paths. D4: Telegram bot and Mini App (session keys, join flow, both chats, vote/bribe UI). D5: Reveal, card renderer, Hall Magic Action. D6: full 8-player playtest in a real group, explorer proof, fixes. D7: video, README, submission. Cut order: Hall/reputation, decoy writes, twists.

## Fogbank  (`realtime-games#1`)
**Tags:** Games, Consumer, Privacy  
**Primitives:** PER, Ephemeral SPL, Ephemeral Accounts, Native Crank, VRF, Session Keys, Magic Actions

**Pitch.** A 100-player top-down extraction shooter where your USDC buy-in is literally your health bar and the map is dark. Every hit moves money from victim to shooter inside a Private ER at 10ms; you can extract with whatever you are carrying at any moment, or die and lose it all. Nobody, including the operator, can see where anyone is or who is carrying the bag, because positions and balances live in the TEE and the program only tells each client what its own character can see.

**Why only MagicBlock.** Fog of war on a public chain is impossible: every position is readable, so a modded client sees the whole map (that is Supersize's world, fully visible by design). On a PER the program computes each player's vision buffer inside the TEE and the permission program restricts each buffer to its owner, so fog is enforced by the chain rather than by the client. The only alternative is a trusted game server, which is exactly what going onchain is supposed to remove. Money-per-hit needs a ledger that updates every 10ms with no fees; on L1 that is 400ms and a fee per hit, and 100 players trading shots would burn more in fees than the hits are worth. Ephemeral SPL plus a private in-TEE ledger makes damage-equals-money viable, and private balances mean nobody knows whom to hunt. 100 players times (Player + Vision buffer) is 200 accounts per match; ephemeral accounts at 109x cheaper make that transient state disposable. Storm, vision passes and extraction timers run on Native Crank inside PER consensus, so there is no server anywhere in the loop.

**Demo moment.** Split screen. Left: a player's view, almost entirely black fog, HUD reads '$9.40 carried'. Two enemies flicker into vision, a firefight, and every hit ticks the HUD '$9.40 -> $9.55 -> $9.70' live while the right half shows the MagicBlock explorer streaming roughly 1,000 tx/s. The presenter then opens a second browser authenticated as the opponent and fetches the first player's Player account from the PER: 'permission denied'. Finally the player hits EXTRACT, a 10-second crank countdown runs, the explorer shows undelegate plus withdraw, and $9.70 lands in Phantom on L1. Program deployed on L1 and cloned into the PER.
Delegated to PER: Match, every Player, pot eATA, player eATAs, LootSeed.
ER-only ephemeral accounts (sponsored by Match): Vision_i per player (ids + positions of enemies within radius, ~1KB), LootCrate accounts (VRF-seeded). Bullets are hitscan, no entities.
Private (owner-only read): Player (position, hp expressed as a ledger in cents, loadout, alive/extracted, kills) and Vision_i. Public: Match, LootCrate positions (loot is bait), pot eATA total.

Crank: vision pass every 100ms sharded into 10 schedules of 10 players each (10x100 distance checks, far under CU); storm tick every 1s shrinks the radius and bleeds cents from outside players into the storm pot; extraction timer of 10s inside an extraction zone. extract = one Ephemeral SPL CPI transfer pot eATA -> player eATA for the ledger balance, undelegate Player + eATA, withdraw to the L1 ATA. Match end = crank finalize: last survivor takes the storm pot, commit Match with a Magic Action that writes results and ELO to the L1 Season PDA. Client: React + PixiJS, authenticated PER websocket subscriptions on own Player + Vision + Match, client-side prediction with reconciliation. A Node bot harness drives 80 session keys for load tests and the demo.

**Novelty vs prior.** Supersize proved 'your mass is your money' but on a fully visible map with public balances; Fogbank inverts it: hidden positions and hidden balances turn chase into hunt, and extraction (the Tarkov model) makes every session a decision about greed. BlitzMine is a mining loop, not twitch PvP; Slimecoin is head-to-head minigames; Tenor, Veil and Ghost Stops are trading. No template covers fog of war, hitscan, crank-driven vision or money-per-hit; the nearest (private-counter, spl-tokens, crank-counter) are single-primitive demos. Nobody in the ecosystem has shipped a real-time hidden-information game on a PER.

**Risks.**
- PER throughput and latency under 100 players sending 10-20 tx/s each is unproven; TDX overhead may push slot time well past 10ms. Load-test on day 1 with bots; the fallback is 25-40 players and the pitch survives that.

- Ephemeral SPL CPI transfer from a PDA authority on extract: if unsupported, fall back to a Magic Action payout from an L1 vault at match end, which kills instant extraction, the best part of the pitch.
- Crank quotas: 10 vision shards at 10Hz plus a storm tick; verify scheduler limits and behavior when a crank ix exceeds CU.
- Netcode is the real week-killer: prediction and reconciliation bugs make it feel bad even if the chain is fast. Grid movement and hitscan weapons exist to make this survivable.
- Skill plus money attracts aimbots and scripted clients that will beat humans; server-side rate limits help but do not solve it. Frame it as agent-friendly rather than pretend otherwise.
- TEE trust: fog and balances are only as private as Intel TDX. Say it out loud in the pitch.

## Mutiny  (`realtime-games#2`)
**Tags:** Games, Social, Privacy  
**Primitives:** PER, VRF, Native Crank, Ephemeral SPL, Session Keys, Magic Actions, Ephemeral Accounts, Private Payments

Real-time movement, 20s kill cooldowns, 45s sabotage timers and 60s councils with automatic tallies need 10ms slots and a crank; on L1 you would have 400ms movement and a bot paying fees to tick timers. **Novelty vs prior.** Veil (v5) was a private DEX frontend that hid swap routing on a PER; it had no order book and no batching. Tenor (v7) was private FX RFQ: bilateral quote requests, not a multilateral book with price-time priority. Ghost Stops (v5) added trailing-stop and bracket order types on top of FlashTrade's public ER; it did not build a venue. BlitzMine and Oobe are unrelated. The official v8 ideas hide positions and leaderboards (private trading competitions), not order flow. No official example is a matching engine; the sealed-auction template is single-lot first-price with a manual end. Nobody has shipped a frequent-batch-auction CLOB on Solana, and the reason is precisely that it needs a private book plus a sub-second consensus clock, which is what PER plus Native Crank provide. The L1 Ticker written by Magic Actions also turns the venue into a composable sandwich-resistant price feed, which none of the prior winners offered.

**Risks.**
- Crank instructions carry a fixed account list, so clear_batch cannot touch dynamically created Seats, eATAs, or ephemeral accounts; settlement is therefore pull-based (settle per Seat). This is sound but means the fill is 'recorded' in the batch and 'credited' one round trip later; if the judges probe it, say so plainly.
- Compute: walking a 512-entry ladder, filling up to 64 orders, and updating the slab in one instruction must fit 200k CU unless the scheduler honors SetComputeUnitLimit (up to 1.4M); if it does not, the per-batch fill cap drops and the book can fall behind under load. Benchmark on day 1.
- Book commits: a 1 MiB delegated slab cannot be committed every 2 s; it is committed only on undelegate. If the PER restarts before commit, resting orders vanish and locked balances need an admin unlock_all that trusts the Seats' locked totals. State this as a known ephemeral-book tradeoff.
- Commit economics: committing Stats every 2 s costs about 100k lamports per commit after the first, roughly 4 SOL/day per market on mainnet; the demo uses 2 s, production would commit on price change or every 30 s.
- Private eATAs are not possible (the eATA is owned by the eSPL program, and only an account's owner program can create its permission), which is why balances live in the private Seat ledger with a pooled vault eATA; this is a custody design, not a pure per-user eATA design, and it must be explained.
- Metadata leakage: the PER hides account contents and (per member flags) transaction logs/messages, but the existence and timing of a wallet's transactions to the PER may still be observable; a dark pool that leaks 'someone big just traded' is weaker than claimed.
- Hardware trust: the book is dark to everyone except Intel TDX and the PER operator (MagicBlock); if the TEE is compromised the pool is a public book. Say it in the pitch before the judges do.
- Scope: a CLOB, batch clearing, eSPL custody, session keys, an MM bot, and a terminal UI in one week is heavy; peg orders, circuit breaker, and fairness roots are the first things to cut.
- Liquidity theater: a dark pool with no flow is a dark room; the demo needs the MM bot and a taker bot running continuously, and the sandwich comparison must be scripted and rehearsed because privacy is hard to show on video.
- Whether accountSubscribe over websocket works with the ?token= URL on the TEE endpoint is undocumented; fall back to 100 ms polling for the private Seat and Tape.
- The brief says PER is devnet-only, but the docs list mainnet-tee.magicblock.app with the same validator key; verify with the engineers, because a mainnet dark pool demo would separate this from every other entry.

**One-week scope.** Days 1-2: Anchor program (Market, Book slab, Seat, Stats, Ticker; place, cancel, settle, clear_batch, deposit_to_seat, withdraw, mirror_ticker action), Delegation Actions that create permissions and schedule the crank, CU benchmarks on local PER (localhost:7799). Day 3: Ephemeral SPL deposit/withdraw through the pooled vault eATA, Magic Action ticker on devnet, session keys via gpl-session. Day 4: Next.js terminal (verifyTeeRpcIntegrity, getAuthToken, private Seat view, public Tape, batch clock), MM bot using quote_sheet and a taker bot. Day 5: the sandwich split-screen demo on devnet, explorer integration proof, README with the FBA rationale, video. Stretch, in order: peg orders and circuit breaker, per-batch Merkle roots, ledger keeper with 64 KB settle batches.

**Extreme extension.** Fairness receipts plus the Nightbook Ticker as an L1 oracle: every 100 ms batch writes a Merkle root over all orders considered; the 2 s Magic Action publishes root and clearing price to the L1 Ticker, which any lending or perps program can read as a dark-pool TWAP that cannot be sandwiched. A trader who kept their private Receipt can later prove, against the published batch leaves, that the batch rule was applied to their order exactly, giving an auditable dark pool, which no CEX dark pool offers. The live party trick: a market-maker bot replacing 1,500 price levels in a single 64 KB transaction ten times per second while the batch clock keeps clearing.

## Backchannel  (`infra-abuse#2`)
**Tags:** Infrastructure, Social, Privacy  
**Primitives:** PER, ER, Ephemeral Accounts, Native Crank, Ephemeral SPL, Magic Actions, Session Keys, Delegation Actions, Oracle

**Pitch.** Backchannel is Kafka on an Ephemeral Rollup: topics are delegated accounts, messages up to 60 KB append into ephemeral log segments at 10 ms slots for zero fees, and the access control is the Private ER permission list itself. Subscribing to a paid topic literally means the program adds your key to the segment's EphemeralPermission members, a Native Crank meters your prepaid Ephemeral SPL balance per second and rewrites you out the moment it runs dry, and every topic's Merkle root is anchored to L1 by a Magic Action so any private message can later be revealed with proof of when it was posted. The flagship app, Receipts, is a paid alpha channel whose track record cannot be faked.

**Why only MagicBlock.** Access-controlled data does not exist on Solana L1 (all account data is public), so every paid feed today is a Telegram group with screenshots as proof. The Private ER makes read permission a program-controlled, per-account primitive that the program flips on-ER with one UpdateEphemeralPermissionCpi; nothing else on Solana lets a program decide who may read an account. The 64 KB transaction is what lets one CPI rewrite a 1,500-member list and what lets a single message carry a whole research note. Ephemeral accounts make 32 KB log segments cost 32 lamports per byte with rent refunded on retention, which is 109x cheaper than L1 and the only way an append-only log at thousands of messages per second is economical. Native Crank meters subscriptions and evicts readers inside consensus with no keeper. The Magic Action after commit is the only atomic bridge that turns 'this hash existed in the TEE at ER time T' into 'this hash existed before L1 slot X', which is what makes private content retroactively provable. Without PER it is public; without the crank it needs a server; without Magic Actions the timestamps are trust-me.

**Demo moment.** Three panes. The publisher types 'SOL long 195 to 210, 2h' into a paid channel; the subscriber's pane shows it 80 ms later; the third pane, a wallet with no subscription and a valid TEE token, requests the same segment and gets nothing back. The subscriber's prepaid USDC ticks down by the cent per second on screen, then the subscriber lets it run dry and the message pane goes dark within one crank tick while the ER explorer shows the permission rewrite. Time-lapse: SOL prints 208. The publisher clicks 'Prove it': the UI opens the message, the Merkle path, and the L1 explorer transaction where a Magic Action wrote that root two hours before the move. Close on the public firehose topic pushing 2,000 messages per second through rolling 32 KB segments.

**Architecture.** L1 ACCOUNTS. Topic PDA [seeds 'topic', publisher, slug]: price_per_sec (USDC), retention_segments, head_seq, current_segment_idx, running Merkle/hash-chain root, member_count, pre-funded lamports for ephemeral rent and permission rent; delegated to the PER validator. Delegation Action on delegate: CreateEphemeralPermissionCpi for Topic (public metadata), create Segment 0 and the Members ephemeral account, ScheduleTask tick at execution_interval_millis=1000, ScheduleTask anchor at 2000 ms. TopicAnchor PDA on L1 [seeds 'anchor', topic]: (root, seq, l1_slot); never delegated; written only by the #[action] anchor_root handler after verifying the injected escrow signer; each write is an L1 transaction the prove page links to. Subscription PDA [seeds 'sub', topic, subscriber]: rate, prepaid balance, paid_until; delegated to the PER; permission is_private:true, members:[subscriber, publisher]. Vault: the Topic's PDA-owned USDC eATA under the Ephemeral SPL program; subscribers' USDC eATAs are deposited through the Global Vault and DelegateEphemeralAta; top_up is a standard SPL Transfer CPI from the subscriber's eATA into the Topic vault eATA plus a credit to Subscription and to the Members table. Publisher withdraw: PDA-signed SPL Transfer from the vault eATA to the publisher's eATA, then commit_and_undelegate the eATA and withdraw from the Global Vault on L1. ER-ONLY EPHEMERAL ACCOUNTS (sponsor = Topic). Segment [seeds 'seg', topic, idx], 32 KB: header plus packed messages (seq, ts, author, len, body); each Segment gets its own EphemeralPermission at creation with is_private:true and members = the current subscriber set with TX_LOGS|TX_MESSAGE|TX_BALANCES flags; free topics use is_private:false. Members [seeds 'mem', topic]: canonical array of up to 1,500 (pubkey, prepaid, paid_until), private to the publisher; this is the fixed account the crank meters against. FLOW. publish(body up to 60 KB), signed by a session key: append to the current Segment; if full, create_ephemeral_segment(idx+1) and create its permission with the current member list in the same transaction (64 KB tx makes the member list fit), advance the hash chain root = H(root || H(msg)). subscribe/top_up (wallet or session key): move USDC into the vault, write Subscription and Members, and UpdateEphemeralPermissionCpi on the active Segment with the new member list. tick crank (every 1 s, fixed accounts: Topic, Members, active Segment, its permission account, permission program): debit prepaid per member, and when any member's paid_until passes, rewrite the active Segment's permission without them; because a crank cannot name dynamic accounts, payments are prepaid into the Topic vault, not streamed from subscriber eATAs. anchor crank (every 2 s or every 100 messages): MagicIntentBundleBuilder.commit(Topic) with CallHandler{anchor_root, compute_units: 30_000} so TopicAnchor on L1 records (root, seq). Retention: tick closes Segments older than retention_segments and rent flows back to Topic. Prove: client-side; the publisher or a subscriber fetches the message through the TEE endpoint, recomputes the chain to the anchored root, and shows the TopicAnchor write transaction with its L1 slot. Oracle (stretch): a Call message type (asset, direction, horizon) scored by a crank against Pyth Lazer for the leaderboard. Reads: clients call verifyTeeRpcIntegrity and getAuthToken, connect with ?token=, and read Segments if they are members; non-members get nothing.

**Novelty vs prior.** The ephemeral-account-chats example is a public chat on ER-only accounts with no permissions, no payments, and no anchoring. The private-payments template moves tokens privately and nothing else. Oobe (v7) is an MCP server for agents. Loofta Pay uses the PER for payments to handles. No prior project used the PER permission list as the product's paywall, and none anchored PER-private state to L1 to make it retroactively provable. Official v8 idea 1 (social tap trading: see friends' moves) is a consumer skin on exactly this primitive, a trade feed is a topic whose member list is your friends, and idea 4 (private jobs board) is a topic with two members; Backchannel is the layer both would be built on, which is the Forge-graduation story.

**Risks.**
- Everything hinges on UpdateEphemeralPermissionCpi accepting large member lists: 1,500 members is roughly 50 KB of account data and instruction data; if the permission account or the CPI caps members far lower, cap topics at 200 subscribers or shard subscribers across duplicate segments. Confirm with the engineers in hour one; ephemeral-rollups-sdk v0.14+ is required.
- Permissions on ephemeral accounts are not documented; the sealed-auction template permissions auction-sponsored PDAs at creation, which suggests it works, but if ephemeral accounts cannot be permissioned the segments become a pre-created pool of 32 delegated L1 PDAs (slower rollover, more rent, still workable).
- Per-segment permission rewrites: every subscribe/evict rewrites the member list on every live segment, O(members x segments) per change; keep only 1-2 live segments private and seal old ones as read-only snapshots.
- Crank fixed-account constraint means payments are prepaid into the vault and metered from the Members table, not streamed from wallets; the UX is 'top up', not 'auto-pay', and evictions are at 1 s granularity.
- The timestamp guarantee is exactly 'existed before L1 slot X' with X set by the anchor cadence; the millisecond ER timestamp is TEE-attested only, and if the PER restarts the bound loosens to the next anchor.
- Selective disclosure: a publisher can post both directions and reveal only the winner; mitigation is all-or-nothing reveal per segment and a leaderboard that scores unrevealed calls as losses, but judges may still poke at it.
- Alpha channels read as financial advice and as degen; frame the product as verifiable timestamps for private feeds with alpha as one demo, and show a second topic (private agent-to-agent messages or a jobs board) to prove generality.
- Anchoring every 2 s costs roughly 100k lamports per commit, about 4 SOL/day per topic on mainnet; production anchors per 100 messages or 60 s.
- Transaction metadata leakage: non-members may still see that a publisher transacted at time T even if content is hidden, which slightly weakens 'private' claims.
- Websocket subscriptions with the token URL are undocumented on the TEE endpoint; poll at 100 ms if needed.
- 64 KB transactions only apply when every writable account is delegated; a publish that also touches an L1 account will silently fall back to the 1,232-byte limit and fail.

**One-week scope.** Days 1-2: Anchor program (Topic, Segment, Members, Subscription, TopicAnchor; publish, subscribe, top_up, tick, anchor_root action, close_segment, withdraw), Delegation Actions for bootstrap, local PER tests including a 1,500-member permission rewrite benchmark. Day 3: TypeScript SDK (createTopic, publish, subscribe, read(fromSeq), prove(seq)) with TEE auth, Ephemeral SPL top-up and withdraw on devnet, Magic Action anchoring on devnet. Day 4: Receipts web app (publisher console, subscriber pane with live balance, non-member pane, prove page linking the L1 anchor), public firehose topic with a 2,000 msg/s load generator. Day 5: explorer integration proof, video, README positioning it as infrastructure. Stretch: Pyth-scored Call Ledger leaderboard; MCP wrapper so agents can publish/subscribe.

**Extreme extension.** The Call Ledger: a public leaderboard of publishers ranked only by revealed, L1-anchored calls, scored inside the ER by a crank reading Pyth Lazer, so private alpha becomes a sortable, unforgeable track record while the content stays paywalled until the author chooses to reveal. Plus two party tricks: a 60 KB message (an entire research PDF) posted in one transaction, and a live eviction where a subscriber's balance hits zero and their read access disappears within one crank tick, visible as a permission rewrite in the ER explorer.

## Candle  (`infra-abuse#3`)
**Tags:** Infrastructure, DeFi, Consumer  
**Primitives:** PER, ER, VRF, Native Crank, Magic Actions, Delegation Actions, Ephemeral Accounts, Ephemeral SPL, Oracle, Session Keys

**Pitch.** Candle is an auction engine that lives inside the Ephemeral Rollup: bids are sealed by Private ER permissions with no reveal phase, the price ticks twenty times a second under a Native Crank, and the moment the auction really ended is chosen retroactively by VRF, so sniping at 0:00.01 is worthless. Settlement is one Magic Action that moves the lot on L1 and calls back into whatever program opened the auction. Two demo apps ship on top: a candle NFT drop with 300 bot bidders, and Dutch liquidations for a mock lending protocol ticking down from the Pyth Lazer price at 50 ms.

**Why only MagicBlock.** A candle auction needs four things at once: bids hidden without a reveal step (PER permissions on each Bid account), a clock that ticks the price and closes rounds inside consensus without keepers (Native Crank at 50 ms), randomness delivered inside the rollup that bidders cannot see before close (delegated-queue VRF), and a settlement that atomically touches L1 escrow and CPIs an arbitrary L1 program (Magic Action with the escrow signer). Polkadot could run candle auctions because those pieces were in-protocol; Solana L1 has none of them at sub-second granularity, and the sealed-auction template has only the first. Dutch liquidations at 50 ms against a 50-200 ms oracle feed are similarly impossible at 400 ms L1 slots with keeper races. On a server, an auction with hidden bids and a random close is just a promise from the operator; inside the TEE with VRF proofs and an L1 audit trail it is verifiable.

**Demo moment.** A 1/1 NFT drop with 300 bot bidders and the judge bidding from a phone through a session key. The countdown hits 0:00; a sniper bot bids +5% at 0:00.03 and the UI shows it leading. Then the VRF callback resolves the candle on screen: 'true close: T minus 3.7 s'. The bidder who led at that instant wins, the sniper's bid unlocks, the Leaders ring is flipped public so anyone can audit the pick, and within about a second the L1 explorer shows the commit plus the Magic Action moving the NFT out of escrow and calling the seller's program. Second tab: a Dutch liquidation for an underwater position ticking down twenty times a second from 1.05x the live Pyth Lazer price until a liquidator bot takes it, with the payment landing in the lending vault via the callback.

**Architecture.** L1 ACCOUNTS. Auction PDA [seeds 'auction', seller, nonce]: mode (Candle | Dutch | Batch), start, end, candle_start, reserve, tick curve params, callback (program id, discriminator, account metas), winner, price, phase; pre-funded lamports for ephemeral rent, permission rent, and the VRF request; delegated to the PER validator for Candle and Batch, to the public ER for Dutch. Delegation Action on delegate: CreateEphemeralPermissionCpi (Candle: is_private:true, members:[seller with TX_LOGS]), create the Leaders ephemeral ring, ScheduleTask tick at execution_interval_millis=50 with iterations = duration/50 plus slack. Escrow on L1: the NFT token account or SPL lot ATA owned by the Auction PDA; never delegated; released only by the #[action] settle handler, which verifies the injected escrow signer, transfers the lot to winner, and CPIs the callback (for the mock lender: on_auction_settled(position, price)). Bidders' USDC eATAs under the Ephemeral SPL program, deposited via the Global Vault and DelegateEphemeralAta; the Auction's PDA-owned eATA holds locked bids; bid does a standard SPL Transfer CPI from bidder eATA to Auction eATA; losers are refunded on the ER by PDA-signed transfer; the seller is paid on the ER and withdraws via commit_and_undelegate of their eATA and a Global Vault withdraw on L1. ER-ONLY EPHEMERAL ACCOUNTS (sponsor = Auction). Bid [seeds 'bid', auction, bidder]: amount, ts, seq; permission is_private:true, members:[bidder]; created in the bidder's own bid transaction, closed at settlement with rent refunded. Leaders: a fixed ring buffer of (slot, leader, amount) appended whenever the leader changes; permission is_private:true, members:[] during the auction, flipped to public at close so the VRF pick is auditable. FLOW (Candle). bid (session key): must exceed the current leader (the program can compare because it runs inside the TEE), lock funds, write Bid, append Leaders. tick crank (fixed accounts: Auction, Leaders, VRF program and delegated queue accounts): when ts >= end, CPI request_randomness on the delegated VRF queue; the VRF callback consume_randomness picks close_slot uniformly in [candle_start, end], sets winner = Leaders entry at close_slot, flips Leaders public, then MagicIntentBundleBuilder.commit_and_undelegate(Auction) with CallHandler{settle, compute_units: 200_000}. Because a crank cannot name dynamic accounts, losers' refunds are pull-based: each losing client calls refund immediately (the UI does it automatically), and any unrefunded Bid can be refunded by anyone after close. FLOW (Dutch). tick every 50 ms decrements price from oracle_price x 1.05 (Pyth Lazer read directly) along the curve; take fills at the current price and triggers the same commit_and_undelegate plus settle action. FLOW (Batch, stretch). bid_curve submits up to 2,000 (price, qty) points in one 64 KB transaction; close computes the uniform clearing price. CPI SDK: candle::cpi::open_auction from any L1 program, with the result delivered as the Magic Action callback carrying committed Auction state.

**Novelty vs prior.** The sealed-bid auction template is first-price with bids hidden by PER permissions, a manual end_auction scan, an undelegate, and a base-layer finalize; no crank, no VRF, no Magic Action, no callback, no live phase. Candle adds a live ascending phase with anti-snipe randomness (never done on Solana), a tick-driven Dutch mode usable for liquidations, atomic L1 settlement and composability through Magic Actions, Delegation Actions that bootstrap the whole auction from one delegate call, and a CPI interface so other programs outsource their auctions. Every prior VRF winner (JungleFun gacha, Bakeland loot, Rosentica, the dice and gachapon templates) used randomness for loot; Candle uses it for time, which is what makes the mechanic new to judges who have seen every VRF demo.

**Risks.**
- VRF inside the PER endpoint is undocumented. If the delegated VRF queue is not served on devnet-tee, the honest fallback is to keep bids on the PER but seed the candle close from a hash of the Pyth Lazer price at close, which is weaker and must be disclosed; ask the engineers in hour one, and record the demo the first time it works.
- Magic Action failure semantics are undocumented: if settle fails on L1 (missing winner ATA, wrong account metas in the callback), the commit may land without the transfer. Pre-create the winner's ATA in the action, make settle idempotent and re-runnable by anyone, and test the failure path.
- Crank fixed-account lists mean the close tick cannot refund 300 bidders; refunds are pull-based (client auto-calls refund), which is fine but must be explained before someone asks why losers' funds are still locked.
- VRF round-trip adds one to two seconds of 'resolving' after the countdown; the UI must make that theater (the candle burning back) rather than dead air.
- Retroactive close confuses first-time viewers; if the candle window is not visible on screen from candle_start, the mechanic reads as a rug. The UI has to sell it in five seconds.
- Three modes is too many for a week; Candle mode ships first, Dutch reuses the same tick, Batch is stretch only. The liquidation demo uses a mock lending program and must not be pitched as a real integration.
- Sniper theater relies on bots; if the sniper wins the VRF draw on camera the demo makes the opposite point. Run several takes or bias candle_start so the window is wide.
- Hardware trust: hidden bids are hidden from everyone except TDX and the operator; a compromised TEE reveals bids to the seller. Say it.
- Auction house is a crowded category; the judges have seen NFT marketplaces. The win condition is the engine (crank, VRF-for-time, Magic Action callback, CPI) and the liquidation story, not the storefront.
- Delegating the Auction to the PER while VRF queue accounts and Pyth Lazer accounts live on the public ER may not be allowed; if cross-ER reads are not available, Dutch mode runs on the public ER (bids are public there anyway) and Candle stays on the PER without the oracle.

**One-week scope.** Days 1-2: Anchor program for Candle mode (Auction, Bid, Leaders; create, bid, tick, consume_randomness, refund, settle action, close), Delegation Actions that create permissions and schedule the crank, local PER tests, VRF-in-PER check on devnet. Day 3: Magic Action settlement with NFT escrow release plus a mock lending program with on_auction_settled; Dutch mode on the same tick with Pyth Lazer; 300-bot bidder script with session keys. Day 4: web app (drop page with the visible candle window, phone-friendly bidding, liquidation dashboard), auditable Leaders reveal. Day 5: devnet video with the VRF resolution and the L1 settlement, explorer integration proof, README with the Polkadot precedent. Stretch: Batch mode with 64 KB demand curves, candle CPI crate.

**Extreme extension.** Liquidation-as-a-service: a mock lending protocol on L1 delegates an underwater position, Candle runs a 50 ms Dutch auction from 1.05x Pyth Lazer, and the winning take settles into the lending protocol's vault through the Magic Action callback, demonstrating an ER auction engine as a drop-in liquidation module for any L1 protocol. The party trick: a token launch where each bidder submits a 2,000-point demand curve in one 64 KB transaction and the ER clears the whole book at a single uniform price in one tick, with allocations paid out as Ephemeral SPL before the L1 commit even lands.

## Keyhole  (`judge-mindset#1`)
**Tags:** DeFi, Social, Privacy  
**Primitives:** PER, ER, Ephemeral SPL, Oracle, Native Crank, Session Keys, Magic Actions, Ephemeral Accounts

**Pitch.** Keyhole is a real-time perps arena where every trader's book is dark by default and the only way to see it is to pay them. Traders sell timed 'keyhole' seats (USDC per minute) to their live positions; buyers watch fills tick in at 10ms and one-tap copy or fade, or turn on same-slot auto-copy so their fill lands in the same ER slot as the trader's. It turns Private ER read-permissions into a market: alpha becomes a subscription, front-running becomes impossible, and nobody can tell who is watching whom.

**Why only MagicBlock.** The product IS the primitive: program-controlled, per-account read access that can be granted and revoked at ER speed (EphemeralPermission members rebuilt via UpdateEphemeralPermissionCpi) exists only in Private ERs. On L1 Solana every position is public, so 'alpha' leaks instantly and copy-bots front-run; ZK systems can hide state but cannot sell selective real-time reads of it. 10ms slots plus gasless session-key taps make 'copied in the same slot' true instead of a 2-second Telegram-bot lag; Native Crank inside the PER enforces seat expiry and liquidations without an off-chain server that could leak books; Ephemeral SPL private transfers hide the subscriber-trader link; Pyth Lazer at 50-200ms makes synthetic perps markable inside the rollup. Remove any one of these and the product collapses into 'a perps DEX with a Discord signals channel'.

**Demo moment.** Split screen. Left: KOL 'degen.sol' trading panel; the positions area is a literal black box to the viewer. Right: a follower taps 'Unlock 0.10 USDC/min' (session key, no wallet popup); the ER explorer shows a private tx with no counterparty, the permission list updates, and within one slot the black box dissolves into a live position table ticking at 10ms against Pyth Lazer marks. The KOL taps 'Long SOL 25x' and the follower's own row appears in the SAME slot, tagged 'copied @ slot N'. Cut: the follower's prepaid balance hits zero, the crank's seat-sweep tx flips the padlock closed and the positions vanish mid-tick. Final beat: round ends, commit + Magic Action pays PnL and seat earnings to L1 USDC, shown on Solscan next to the ER explorer tx.

**Architecture.** L1 (Anchor): Arena PDA (round config, USDC vault authority; public). Market[asset] PDA (Pyth Lazer feed id, OI, funding) delegated to the TEE validator MTEWGuqxUpYZGFJQcp8tLN7x5v9BSeoFHYWQQ3n3xzo and left public (members=[]). Trader PDA per wallet (collateral, positions[8], realized PnL, seat price, seat earnings) delegated to TEE with pre-funded lamports, init_permission then set members=[trader] (TX_LOGS|TX_MESSAGE|TX_BALANCES). Seat PDA per (buyer, trader) (rate, prepaid balance, expiry) delegated, members=[buyer, trader]. Follower PDA (auto-copy collateral + max size) delegated, members=[follower]. Tape: ephemeral account per trader sponsored by the Trader PDA, ring buffer of last 256 fills, member list mirrored from Trader. Read gating: grant_seat/revoke_seat rebuild the full member list on Trader and Tape (docs: members are rebuilt on every update; realloc via EphemeralPermission::size_of(N)). Oracle: program reads PDA ['price_feed','pyth-lazer',feedId] i64 at offset 73 for SOL/BTC/ETH plus one requested pump.fun feed. Crank: ScheduleTask at round start with finite iterations and an arena.live guard flag: liquidate_sweep every 100ms; seat_sweep every 1000ms that debits prepaid balances and revokes exhausted seats. Same-slot auto-copy: open_position takes up to 16 Follower PDAs as remaining_accounts and sizes proportional fills inside the trader's own tx (1.4M CU budget); larger followings fan out via crank one slot later. Settlement: round end = commit_and_undelegate(Trader) with MagicIntentBundleBuilder...add_post_commit_actions([payout]) so a Magic Action moves collateral + PnL + seat earnings from the Arena vault to the trader's ATA atomically; eATAs undelegateIx() then withdrawSpl(). Leaderboard PnL is private during the round and becomes public only at commit.

**Novelty vs prior.** Veil hid a DEX frontend and Tenor hid RFQ quotes: both make state invisible; Keyhole makes visibility itself a priced, revocable good. Ghost Stops added order types on FlashTrade; Keyhole is social and private, not an order-type. BlitzMine and Oobe are unrelated. It fuses MagicBlock's own v8 ideas #1 (social tap trading) and #2 (private competitions) and goes past both with paid seats, crank-revoked access, same-slot auto-copy and a hidden-until-commit leaderboard. No official example (counter, private-counter, sealed-auction, binary-prediction, Lever) does dynamic member lists, paid reads, or crank-driven revocation.

## Felt  (`judge-mindset#2`)
**Tags:** Games, Consumer, Privacy  
**Primitives:** PER, ER, VRF, Native Crank, Session Keys, Ephemeral SPL, Magic Actions, Ephemeral Accounts

**Pitch.** Felt is real-money no-limit Texas Hold'em where the deck and every hole card live inside a Private Ephemeral Rollup: no dealer server, no mental-poker cryptography, no block waits. The first poker room where the house is a TEE and the rake is zero.

**Why only MagicBlock.** Hidden hole cards with fast play has been the canonical 'impossible on-chain' game: mental-poker protocols need multi-round MPC or ZK per shuffle (seconds and gas per hand), and every shipped 'on-chain poker' uses an off-chain dealer that holds the deck. PER makes the deck an on-chain account nobody can read (its only permission member is a PDA, which can never sign the TEE challenge), each hole-card account readable only by that seat, and the entire game engine a Solana program executing at 10ms for free. Crank auto-fold inside ER consensus removes the timeout server; the delegated VRF queue gives sub-100ms provable shuffles; Ephemeral SPL makes chips real USDC; Magic Actions make payout atomic with the commit. Nowhere else do these pieces exist together.

**Demo moment.** Two phones on a table plus a laptop. The deal lands: both phones show the same ER explorer signature, but phone A shows A-spade K-spade and phone B shows 7-diamond 2-club. **Architecture.** L1 (Anchor): Table PDA (config, seats[9] with stacks, pot(s), board, street, action-on, shot clock; public, members=[]), Seat PDA per (table, player) (stack, status; public), Escrow USDC authority PDA. Deck: ephemeral account (52 bytes + cursor + seed) sponsored by Table, init_permission then members=[Table PDA] with no flags, so no human can obtain a read token (docs confirm PDAs are valid members). Shuffle: at hand start the program requests randomness from the delegated VRF queue (writable only inside an ER); each seated player has already committed a 32-byte nonce hash at buy-in and reveals it in a TX_MESSAGE-hidden tx; final seed = hash(vrf || nonces || hand_no); in-program Fisher-Yates (about 20k CU). ## Sotto  (`judge-mindset#3`)
**Tags:** AI/Agents, Payments, Privacy  
**Primitives:** PER, ER, Ephemeral Accounts, Ephemeral SPL, Private Payments API, VRF, Native Crank, Magic Actions, Session Keys

**Pitch.** Sotto is a private inference market where prompts and responses live in a Private Ephemeral Rollup and tokens stream on-chain as they are generated. **Why only MagicBlock.** Prompts and responses are 5-50KB, impossible inside Solana's 1,232-byte transaction; the ER's 64KB transactions and 10MiB accounts let a whole prompt land in one tx and a whole response live in one account. PER makes the job account readable only by requester plus provider, so the marketplace is public while content stays private; per-token eSPL payments hide who buys inference from whom. Crank enforces SLAs and slashing inside consensus, VRF assigns providers so nobody self-deals, Magic Actions push reputation and stake to L1 atomically on commit, and the Private Payments API on mainnet lets providers cash out to a stealth handle today.

**Demo moment.** A Claude Code session runs 'sotto ask summarize this 30-page contract'. Audit (spot-check assignments; public). ## Placard — sealed real-time ad exchange  (`wildcard#1`)
**Tags:** Infrastructure, AI/Agents, Privacy  
**Primitives:** PER, ER, Ephemeral Accounts, Native Crank, Magic Actions, Session Keys, Ephemeral SPL, Oracle

**Pitch.** Placard is an onchain real-time-bidding (RTB) ad exchange where every impression on a dapp, wallet, explorer or Blink is a sealed second-price auction that opens, clears and settles in under 100ms inside a Private Ephemeral Rollup. Advertisers (mostly AI bidding agents) upload private bid curves, viewers hold private interest profiles, the TEE matches them and publishes only the winning creative and the clearing price. Publishers are paid in USDC on every commit via Magic Actions, and nobody -- not the publisher, not rival advertisers, not Placard -- ever sees a losing bid or a viewer's profile.

**Why only MagicBlock.** RTB has a hard ~100ms deadline and a per-auction value of fractions of a cent. On Solana L1 a 400ms slot already blows the deadline, a 5,000-lamport base fee exceeds a $0.002-CPM impression, and bids on a public ledger leak to competitors (commit-reveal needs two round trips and cannot clear in 100ms). The ER gives 10ms slots, zero fees, 64KB transactions (one tx can evaluate dozens of bid curves), and Ephemeral Accounts that make a per-impression auction object 109x cheaper than L1 rent and refundable on close. The PER (TDX) is what makes sealed bidding and private profiles possible with no reveal phase: the program computes over every party's private state inside the enclave and publishes only the result. Native Crank does budget pacing and stale-impression cleanup with no offchain keeper. Magic Actions turn a commit into an atomic L1 USDC payout to the publisher. Remove any of ER/PER/crank/actions and it is either too slow, too expensive, leaks bids, or needs a trusted server -- i.e. it becomes Google.

**Demo moment.** Split screen. Left: a fake Solscan-style explorer page with three ad slots. Right: the MagicBlock ER explorer streaming txs. Presenter hits reload; three creatives flip in ~120ms and three ER txs land: open_impression, clear_auction, close_impression. Then the load generator switches on: a counter climbs 'auctions cleared: 4,000 ... 9,000 ...' while five advertiser-agent dashboards show win-rate and spend moving; one agent visibly raises its curve for the 'DeFi power user' segment and starts winning it. Finally a commit lands and a Magic Action pays the publisher's L1 USDC ATA, shown on Solana explorer. 'Every ad you just saw was a sealed auction that nobody could read.'

**Architecture.** L1 (Anchor, program cloned to ER): Exchange config PDA; Publisher PDA and Slot PDAs (size, category, floor CPM); Advertiser PDA (USDC deposited into an L1 vault PDA, mirrored as an internal ledger); AdvertiserCurve PDA per advertiser (base CPM, per-segment multipliers, pacing cap); Earnings ledger PDA per publisher; UserProfile PDA per viewer (segment bitset). Delegated to the TEE validator MTEWG...: Slot PDAs (public, permission members = []), AdvertiserCurve PDAs (members = [advertiser]), Advertiser ledger (members = [advertiser]), UserProfile (members = [viewer] -- the viewer can audit what is known about them, advertisers cannot), Earnings ledger (members = [publisher]); a public BidBook PDA holds only an eligibility bitmap per slot category to bound accounts per auction. Ephemeral Accounts: one Impression account per ad request, sponsored by the Slot PDA, created by open_impression with (slot, coarse context, viewer pubkey), written by clear_auction with (winner, creative id, clearing price), closed by crank after 30s with rent refunded to the sponsor. Auction (runs inside the TEE so it may read private curves and profiles): second-price with floor, pacing check against the advertiser ledger, debit winner ledger, credit publisher ledger; one tx per impression loading Slot + BidBook + ~30 eligible AdvertiserCurve accounts + UserProfile + Impression, within 1.4M CU. Crank: ScheduleTask every 500ms -> pace_budgets (reset per-second spend windows) and sweep_impressions (close stale ephemeral accounts), finite iterations with a guard flag. Session Keys: bidding agents sign update_curve with a session scoped to their AdvertiserCurve; the publisher JS snippet signs open_impression with a delegated slot key. Settlement to L1: a crank task every N seconds (or on an earnings threshold) commits the Earnings ledger with a Magic Action that does an L1 SPL transfer vault -> publisher USDC ATA; advertiser top-ups are plain L1 deposits credited on the ER via a delegation action; undelegate on exchange close. Ephemeral SPL (stretch): replace internal ledgers with eATA balances so advertisers withdraw unspent budget without an undelegate cycle. Oracle: advertisers funding in SOL or a pump.fun token get budgets marked-to-USD from the Pyth Lazer feed PDA so bids stay USD-denominated. Profiler: an offchain script, with viewer consent in the demo, derives segments from a wallet's public history (SOL > 1, used Jupiter, holds an NFT) and writes the bitset to the viewer's private profile PDA.

**Novelty vs prior.** No Blitz winner or MagicBlock example touches advertising. Tenor (FX RFQ) and Veil (DEX) are trading venues for humans, Ghost Stops is order tooling on FlashTrade, BlitzMine is a game, Oobe is an agent MCP. The sealed-auction template is one item, one round, humans bidding once. Placard is thousands of parallel sealed auctions per minute; bids are standing private curves evaluated by the TEE rather than per-round submissions; there are two independent private parties (advertiser curves and viewer profiles) whose data never meet outside the enclave; per-auction state is an Ephemeral Account that lives 30 seconds; settlement is continuous via crank-triggered commits with Magic Action payouts. ## Turnstile — sealed-bid ticket drops with a live clearing price and locked resale  (`wildcard#2`)
**Tags:** Consumer, Payments, Privacy  
**Primitives:** PER, ER, Session Keys, VRF, Native Crank, Magic Actions, Ephemeral Accounts, Ephemeral SPL

**Pitch.** Turnstile replaces the Ticketmaster stampede with a 60-second sealed-bid, uniform-price seat auction inside a Private Ephemeral Rollup: tens of thousands of fans tap bids gaslessly with session keys, individual bids are invisible to everyone including the venue, and the only thing on screen is a live seat map whose per-section clearing price updates every 10ms as the TEE recomputes the k-th highest bid. Winners all pay the same clearing price, ties and a face-value lottery tier are settled by VRF, tickets are bound to the buying wallet, and the only way to resell is through the venue's private, price-capped resale book. Bots gain nothing from speed, scalpers gain nothing from resale, and the artist gets the surplus instead of StubHub.

**Why only MagicBlock.** A ticket drop is a 60-second burst of 50k+ writes to a few hot accounts. On L1 that is a priority-fee war (bots win by paying more) at 400ms cadence with public bids that snipers read; a commit-reveal sealed auction fixes bid privacy but kills the live price (nothing can be aggregated until reveal) and doubles the transactions. The ER absorbs the burst at 10ms slots, gasless, with session keys so a fan taps 'raise' without a wallet popup. The TEE lets the program hold every sealed bid, recompute the uniform clearing price continuously, and publish only that aggregate -- private inputs, public live output -- which is impossible on any public chain and impossible with commit-reveal. VRF gives a provably fair lottery tier and tie-break the venue cannot rig. Native Crank closes the round at T+60s inside consensus with no keeper to bribe. Magic Actions make the commit atomic with the L1 payout to the artist. The resale book needs PER too: a price cap only works if buyers cannot be identified and paid off-chain, so buyer and seller identities and prices live in the enclave with read permission limited to the two parties and the venue.

**Demo moment.** A countdown hits zero on a 10,000-seat arena map. The presenter's phone taps 'bid $80' for section 112 with no wallet popup. The load generator releases 40,000 simulated fans on session keys and the map catches fire: section colors shift as clearing prices climb $45 -> $62 -> $71 at 10ms cadence while a 'sealed bids received' counter spins past 30,000 and the ER explorer streams txs. The presenter raises to $95 and section 112 flips green: 'you are above clearing'. At T+60 the crank closes the round, VRF breaks a three-way tie on the last seat, the presenter's ticket appears bound to their wallet, and a Magic Action pays the artist's USDC ATA on L1. **Architecture.** L1 (Anchor): Event PDA (organizer, drop start/end, USDC vault PDA, artist ATA); Section PDAs (supply k, face value, floor, mode auction|lottery); Ticket PDAs (owner, section, seat, status -- ownership is a program record, no SPL/Token-2022, which makes wallet-binding and check-in trivial); Fan ledger PDA (USDC deposited into the vault before the drop; internal balance locked against bids); ResaleListing PDAs. Delegated to the TEE validator: Section PDAs (public, members = [] so anyone can watch the map: supply, live clearing_price, bid_count); one BidBook Ephemeral Account per section sponsored by the Section PDA (members = [organizer] for post-mortem audit only; sorted array of (bidder, amount); 64KB tx size and resizable ephemeral accounts make a 5,000-bid book per section feasible); Bid PDAs per (fan, section) (members = [fan]); Fan ledger PDAs (members = [fan]). Bidding: place_bid / raise_bid signed by a session key scoped to the fan's Bid PDA; program locks the amount in the fan ledger, inserts into the BidBook, and recomputes the k-th highest into Section.clearing_price (per call for small k; for large sections batch the recompute via a 100ms crank tick). Close: Native Crank ScheduleTask at drop_end -> close_section: winners = top-k, boundary ties resolved by a delegated VRF callback, every winner pays clearing_price with the remainder unlocked, losers unlocked, Ticket PDAs created (seat assignment by a second VRF in lottery mode); commit_and_undelegate Section and ledgers with Magic Actions: L1 SPL transfer vault -> artist ATA for the section's revenue; undelegated fan ledgers let losers withdraw refunds on L1. Lottery tier: face value only, entrants chosen by VRF at close. Resale: Ticket PDA re-delegated to the TEE with members = [owner, organizer]; list_for_resale(price <= face) writes a private listing; buy_resale from any deposit-funded wallet moves ledger balances and rewrites owner; commit mirrors owner to L1; seller and buyer identities never leave the enclave. Check-in: gate app shows a challenge, fan wallet signs, check_in on the ER marks the Ticket used, commit. Ephemeral SPL (stretch): fans deposit via delegateSpl into eATAs, bids lock eATA balances, winner payments become private transferSpl to the event eATA, undelegate -> withdrawSpl for refunds, removing the internal ledger. Oracle (optional): SOL deposits marked to USD via the Pyth Lazer SOL/USD feed PDA so face values stay USD-denominated.

**Novelty vs prior.** No Blitz winner has touched ticketing, and MagicBlock's sealed-auction template is one item, one winner, no live aggregate, no resale, no burst. Turnstile is (1) multi-unit uniform-price with thousands of bidders per section, (2) a live clearing price computed from sealed bids -- a private-input/public-output primitive the template does not attempt, (3) VRF-settled ties and lottery tiers, (4) a second private market (resale) where identity confidentiality is the anti-scalping mechanism, (5) burst-scale session-key UX. Unlike Tenor, Veil and Ghost Stops (all trader tooling) it is a consumer product ordinary people understand in five seconds, which matters for virality and for the Founders Camp story.

**Risks.**
- Crypto ticketing is a graveyard (GET Protocol, YellowHeart, Seatlab); judges have seen 'NFT tickets' many times. Lead with the auction mechanism and the sealed/live-price property, never with NFTs.
- Fans hate auctions; a uniform-price auction reads as surge pricing. The face-value lottery tier is not optional, and the surplus-to-artist message must be explicit.
- Wallet-binding is not identity-binding: a scalper can sell the wallet. Without KYC the anti-scalping story is 'resale is capped and private', not 'resale is impossible'. Say exactly that.
- 40,000 simulated bidders is a load test, not adoption; measure real ER throughput on devnet-tee and put the real number on the slide -- it may be a few hundred bids per second, which still crushes L1 but is not 40k in 60s.
- BidBook growth: a 5,000-entry sorted array inside one ephemeral account needs careful resize and CU budgeting; per-bid k-th-highest recompute can exceed CU for large sections, so batch via crank.
- Sealed-auction template similarity is a judging risk; the three-levels-further argument has to be visible in the demo, not just the README.
- PER is devnet only; there is no venue partner; the artist payout goes to a wallet you control. Be honest that this is a mechanism demo, not a launch.

**One-week scope.** Day 1-2: Anchor program: event/section/ticket/ledger, delegate sections and ledgers to the TEE validator, init_permission + set_privacy for bids and ledgers, place/raise bid with k-th highest recompute, unit tests on localnet. Day 3: crank-scheduled close, VRF tie-break and lottery mode via delegated VRF callback, commit with Magic Action payout, refunds via undelegate. Day 4: seat-map frontend (SVG arena, 10k seats, sections colored by clearing price, WebSocket subscription to Section accounts on the ER), session-key onboarding, deposit flow. Day 5: load generator (N session-key bidders with a bid distribution), TEE attestation and token flow, 'read bid without token fails' proof screen, private resale list/buy. Day 6: check-in QR flow, mobile layout, metrics, polish. Day 7: video, README, explorer proof, submit. Cut list: Ephemeral SPL (keep the internal ledger), oracle, check-in.

**Extreme extension.** The ticket is a session key. At the event every Ticket PDA holder auto-joins a halftime crowd game running on the ER: the arena map becomes a Pong board where each section's paddle moves by majority tap at 50ms crank ticks and VRF picks a seat number to win the pot -- 10,000 phones, one game, zero gas. And the seat map never stops trading: from close until doors open the private resale book runs continuously with a crank-driven price cap that decays toward face value as showtime approaches, so a ticket's price can only go down after the primary sale.

## Ajo — crank-run private savings circles with Dutch-clock rounds  (`wildcard#3`)
**Tags:** Payments, Consumer, Privacy  
**Primitives:** PER, Native Crank, Session Keys, VRF, Ephemeral SPL, Private Payments, Magic Actions, Oracle

**Pitch.** Ajo (also esusu, susu, tanda, chit fund) is the world's oldest financial product: a group pools a fixed amount every period and one member takes the pot. Hundreds of millions of people use it, and the two things that break it are the collector who runs off with the money and everyone knowing your finances. Ajo puts the circle inside a Private Ephemeral Rollup: a Native Crank is the collector (it debits contributions, runs the round, pays the pot, slashes defaulters), circle finances are readable only by circle members, and each round is a live 60-second Dutch-clock auction -- the payout ticks down every 100ms until one member taps to take it, with the discount instantly split to everyone else. Contributions arrive via stealth handles so nothing on L1 links you to your circle.

**Why only MagicBlock.** Three things need ER/PER specifically. (1) The Dutch clock: a descending-price auction where the first tap wins is only fair with sub-slot latency; at 400ms L1 slots the winner is whoever's RPC is closest, and every tick costs a fee. At 10ms slots with gasless session-key taps a 100ms clock is fair and free, and VRF resolves same-slot ties. (2) The collector: Native Crank runs the round schedule, auto-debits contributions from members' ephemeral balances, and executes payouts inside ER consensus -- no organizer key that can abscond, no offchain keeper. (3) The social privacy of real ajo: inside the circle everyone sees everything, outside nobody sees anything. PER permission groups map to this exactly (members = the circle for circle state, members = [you] for your own ledger and reputation), and Private Payments stealth handles make L1 contributions unlinkable to the circle. On a public chain, ajo becomes a public ledger of who is broke this month, which is why nobody uses the onchain ROSCAs that already exist.

**Demo moment.** Twelve phones (or twelve browser tiles) in a circle named 'Lagos Tech Ajo', $100 each, round 3 of 12. The crank fires: twelve balances drop by $100 at once and the pot reads $1,200. A Dutch clock starts descending -- $1,200, $1,190, $1,180 -- one number changing every 100ms across all twelve screens in sync. At $1,090 one phone taps 'take it'. The pot lands in that member's balance and the $110 discount splits eleven ways, every other balance visibly ticking +$10 within a second; the ER explorer shows the tick txs, the tap, and the payout. The presenter opens a thirteenth phone that is not in the circle: the circle query returns 'permission denied', and the L1 explorer shows only stealth-handle deposits with no link to any of the twelve wallets. 'The collector is a crank. Nobody outside the circle knows it exists.'

**Architecture.** L1 (Anchor): Circle PDA (member set, contribution amount, period, mode dutch|sealed|lottery, collateral requirement, round count); Member PDA per member (optional USDC collateral in a vault PDA, join status); Reputation PDA per wallet (rounds completed, defaults, discount history). Delegated to the TEE validator: Circle state PDA (round, pot, clock_price, phase, timer; permission members = all circle members so the whole circle watches the clock and outsiders cannot read it); MemberLedger PDAs (members = [member]: balance and contribution history are yours alone, while the program still reads them inside the enclave to debit contributions and detect defaults); Reputation PDAs (members = [member]; other circles read them inside the enclave at join time and publish only 'eligible: yes/no'); sealed-bid PDAs in sealed mode (members = [member]). Money: members deposit USDC through Ephemeral SPL (delegateSpl into eATAs) or via the Private Payments API to the circle's stealth handle (lagos-tech@magicblock.id); balances live as ephemeral SPL balances; the pot is an eATA owned by the Circle PDA; payouts are private transferSpl to the winner's eATA; withdraw = undelegate -> withdrawSpl. Fallback if the eATA program-authority approval is fiddly: internal ledgers plus Magic Action L1 transfers on commit. Crank: ScheduleTask at round start -> collect (debit each MemberLedger by the contribution; on shortfall mark default and slash collateral into the pot); ScheduleTask every 100ms with finite iterations -> tick (clock_price -= step until floor); tap -> settle_round (pay pot to taker, distribute discount pro-rata, advance round, stop ticking via guard flag); clock at floor with no taker -> VRF picks the recipient (lottery fallback). Sealed mode replaces the clock with sealed discount bids and a single crank close. Session Keys: 'take it' and 'bid' are session-signed so a tap is a tap. VRF: lottery mode, same-slot tie-break on taps, and stranger-circle matching (VRF shuffles the waitlist into circles of N). Settlement to L1: after the final round, commit_and_undelegate the Circle and MemberLedgers with Magic Actions that return collateral from the vault to each member's ATA and write Reputation deltas; mid-cycle, members can undelegate their own eATA to withdraw earned discounts any time. Oracle: SOL-denominated circles read the Pyth Lazer SOL/USD feed so the contribution is a fixed USD value each round. Client: verify TEE attestation, sign the challenge, hold one token per member; a non-member client demonstrably cannot read circle state.

**Novelty vs prior.** Nothing in Blitz history or the MagicBlock example set is a savings product, and none of the ecosystem darlings (FlashTrade, Supersize, JungleFun, Loofta Pay) target group finance. Loofta Pay uses PER for private one-to-one payments; Ajo uses PER for a multi-party private ledger where the enclave computes over everyone's balances and publishes only round outcomes. The Dutch-clock round is a real-time mechanism, not a form submission, and the crank-as-collector framing turns Native Crank from a scheduling convenience into the product's trust model. It is the one of the three with the most obvious Founders Camp story: a mobile app for a market with hundreds of millions of existing users and a known fraud problem.

**Risks.**
- Speed is only load-bearing in Dutch mode. If a judge asks why a monthly savings circle needs 10ms slots, the answer is the clock and the gasless taps; sealed and lottery modes would be fine on L1 plus PER. Lead the demo with the clock.
- Collateral defeats the purpose: real ajo works because it needs no collateral, and asking the unbanked to lock USDC first is a contradiction. Stranger circles need collateral or credit history; friend circles can run collateral-free on reputation alone. Ship friend circles first and be explicit.
- Regulatory: chit funds are regulated in India and ROSCAs draw scrutiny in several markets; the Dutch discount is functionally interest. Position as a tool for existing informal circles, not a lender.
- Judges may not know what ajo is; you have ten seconds to explain it or you lose the room. Open the video with a one-sentence definition and a screenshot of a real WhatsApp circle.
- PER is devnet while Private Payments is mainnet; the stealth-handle deposit and the circle logic cannot run on the same network in the week. Demo both and say which is which.
- Crank has no documented cancel; a 100ms tick task with a guard flag still burns iterations after a tap -- budget finite iterations per round and test the guard.
- It is fintech, not trading/games/agents, which is outside the judges' stated sweet spots; the consumer-virality argument rests on the mobile UX being genuinely good, which is a lot for one week.
- Default handling is where every onchain ROSCA died. If a member stops paying mid-cycle with no collateral, the math must degrade gracefully (smaller pot, reputation hit) rather than freezing the circle.

**One-week scope.** Day 1-2: Anchor program: circle/member/ledger/reputation, delegation to the TEE validator, init_permission + set_privacy with circle-member groups, collect/tick/tap/settle_round, unit tests with a mocked clock on localnet. Day 3: Native Crank scheduling (collect at round start, 100ms tick with finite iterations and guard flag), VRF lottery fallback and tie-break, session keys for taps. Day 4: Ephemeral SPL deposit/transfer/withdraw for balances and pot (fall back to internal ledger if the eATA authority flow blocks), Magic Action collateral return on final commit. Day 5: mobile-first React app: create/join circle, balances, round screen with the synchronized clock via ER WebSocket, TEE attestation and token, non-member 'permission denied' screen. Day 6: Private Payments stealth-handle deposit to the circle handle (mainnet path), reputation write-back, sealed mode, polish. Day 7: video with twelve tiles, README, explorer proof, submit. Cut list: sealed mode, oracle, stranger matching.

**Extreme extension.** Compressed time: for the demo a 12-month circle runs as 12 rounds of 60 seconds, so the video shows an entire year of ajo -- every contribution, every Dutch clock, every discount dividend, every default slash -- in twelve minutes on twelve real phones with every tx on the ER explorer. Then stranger circles matched by VRF from a global waitlist, admitted by a TEE-private reputation check that reveals nothing but 'eligible', and circles of circles where each circle's pot feeds a federated pot with its own clock.
